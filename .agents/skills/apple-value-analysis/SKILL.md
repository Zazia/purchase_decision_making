# 苹果产品价值分析与购买决策 SOP

## 何时调用本技能 (When to Invoke)

**当出现以下任一情况时,必须调用本技能(而非直接回答或单纯联网搜索):**

- 用户想购买苹果设备(Mac / iPhone / iPad / Apple Watch / AirPods / Vision Pro 等),需要决策"买哪款、买新品还是二手、用几年划算"
- 用户想对比苹果产品**各代机型**或**不同持有期**的性价比 / 月均成本 / 保值率
- 用户询问苹果产品的**保值率、残值、贬值速度**(如"M2 现在还值多少钱""还能撑几年")
- 用户在多款苹果设备间纠结"**先换哪个 / 哪个更值得换**"(多品类对比)
- 用户给出**预算 + 品类**,要求推荐最划算的购买方案(如"5000 预算买 Mac mini,怎么买最值")
- 用户明确要求基于数据做**购买决策报告**或**性价比量化分析**
- 用户想**预估涨价 / 新品发布对二手市场的影响**(如"这次涨价后二手价会怎么走""老款现在卖还是等发售后卖""等新品发布再买旧款能便宜多少")

### 触发示例(用户原话)

- "想买个 Mac mini,预算 5000 以内,不知道用几年划算"
- "iPhone 15 和 16 哪个值得买?用两年哪个省"
- "MacBook Air M2 二手现在入手合适吗"
- "手机和电脑哪个该先换"
- "帮我分析下苹果产品保值率,做个购买决策报告"
- "M4 新品国补后还值得买吗,对比二手"

### 不应调用的情况

- 仅查询苹果产品**参数 / 跑分 / 发布日期**(直接 WebSearch 即可,无需全流程分析)
- **非苹果产品**(本技能常量库仅覆盖苹果全系,不适用安卓/Windows 设备)
- 仅比较**电商平台当前价格**、无持有期 / 残值 / 性价比分析需求
- 用户只想要一段口述建议,明确表示不需要报告或量化计算

## 本技能做什么 (What This Skill Does)

基于 `constants.json` 常量数据库(保值率曲线、芯片跑分、内存/存储权重、发布节奏、维修成本、实时市场价快照等,获取方式见「依赖文件」)与按需校验更新的市场价快照,执行**场景路由 + 7 步标准流程**:确定候选方案 → 宏观因素扫描与常量分级校验 → 校验市场价快照并按需更新 → 计算持有期平均性能满足度 → 计算月均成本(含预期维修成本) → 帕累托前沿分析 → 结论先行的 HTML 报告。核心输出为(月均成本, 持有期平均性能)平面上的**帕累托前沿**,前沿上的非劣解即为合理购买方案。

## 依赖文件

- **`constants.json`**:唯一常量数据源。SOP 版本追踪方法论(流程/公式/规则),constants.json 版本追踪数据(保值率/跑分/快照),两者独立演进——只要本文件引用的字段结构存在即可正常工作,不要求版本号一致
- **实时市场价快照**:存储于 constants.json 内,含真实交易渠道价格(苹果官网/京东自营/闲鱼/爱回收/京东拍拍)及符合5项标准的可信二手资料价格。下次分析优先校验快照是否需更新,避免每次全量搜索;分级使用规则见步骤3.0
- **工具脚本**(`scripts/`,随技能分发,纯 Node 零依赖):
  - `query-constants.mjs`:**constants.json 查询的唯一入口**。步骤流程中所有"查 constants.json"一律通过它按键路径取值——`node scripts/query-constants.mjs <键路径>`(如 `芯片性能跑分.Mac芯片.M2`),不知道键名时先 `--list <键路径>` 列子键或 `--search <关键词>` 搜键名。键路径用 `.` 分隔,脚本自动适配含点号的键名(最长键名优先)。**禁止整读 constants.json**(1900+ 行,整读浪费上下文且易遗漏;rg/grep 在 PowerShell 下搜中文键还有引号坑)
  - `load-engine.mjs` / `engine-smoke.mjs`:引擎加载器与冒烟检查,见「引擎调用」

### constants.json 的获取与更新机制

本技能以**目录为分发单元**(SKILL.md + reference/ + examples.md + CHANGELOG.md + scripts/),constants.json 无需随分发,执行时自动从远程获取最新版,实现数据维护集中化、分发轻量化。

**远程仓库**(双源,Gitee 优先):
```
主源: https://gitee.com/zezia/purchase_decision_making/raw/main/.agents/skills/apple-value-analysis/constants.json
备份: https://raw.githubusercontent.com/Zazia/purchase_decision_making/main/.agents/skills/apple-value-analysis/constants.json
```

**获取规则**(每次技能被调用时,步骤0之前执行):
1. 检查 SKILL.md 同目录是否存在 `constants.json`
2. **本地不存在** → WebFetch 从主源获取(超时/不可达自动回退备份源),保存到同目录,供本次及后续分析使用
3. **本地存在** → 读取 `metadata.last_updated`:距今 ≤ 7 天 → 直接使用,跳过网络获取;> 7 天 → 提示用户"数据已过期(上次更新: YYYY-MM-DD),正在从远程获取最新版"后覆盖本地
4. **双源均不可达**:本地有旧版 → 使用旧版,报告标注"⚠️ 常量数据可能过期(YYYY-MM-DD,远程获取失败),市场价快照等时效性数据可能不准确";本地无文件 → 提示用户手动从任一远程地址下载并放置于同目录,终止执行

**关键原则**:是否更新只看 `metadata.last_updated` 日期,**不依赖版本号比对**——远程 constants.json 约每周更新一次(市场价快照回写为主),版本号高于本地 SOP 版本是正常现象。分析过程中本地回写的市场价快照仅用于本次分析,不自动推送远程;远程仓库由维护者定期合并各分析节点的快照更新。Gitee 与 GitHub 双仓库内容保持同步(策略见仓库 README.md)。

## 引擎调用(可选加速路径)

本技能的帕累托前沿算法已抽离为独立 TypeScript 引擎包 `apple-value-engine`(仅存在于本仓库 `packages/apple-value-engine/`;技能分发到仓库外使用时引擎不存在)。**引擎只是计算加速器,不是依赖**:文字路径(步骤4-6公式)才是规格本身,引擎是它的等价实现,两条路径输出一致。引擎不可用时走文字路径,分析结果不受影响。

### 引擎冒烟检查(步骤0执行,约5秒)

每次分析开始时运行一次,提前判定本次走哪条路径:

```
node <技能目录>/scripts/engine-smoke.mjs
```

脚本自动定位引擎并做真实微计算,输出 `PASS`(含引擎入口绝对路径)或 `FAIL`(含各候选路径失败原因):

- **PASS** → 进入计算阶段时走引擎路径,跳过步骤4-6手动计算
- **FAIL** → **立即锁定文字路径**,在报告中标注"⚠ 本次走文字路径(引擎冒烟未通过)"。**禁止进入引擎诊断**:不排查构建、不读源码、不尝试修复;唯一正确动作是把冒烟输出记录进报告并告知维护者

> 引擎 dist 产物为纯 ESM(2026-08-27 P0 修复: tsconfig 改 NodeNext 重建,旧的 CJS 语法 + `"type":"module"` 冲突已消除,直接 import 可用),`load-engine.mjs` 加载器兼容新旧两种格式,冒烟 PASS 即代表可正常调用。

### 信任边界(防呆红线)

- **引擎是黑盒**:vitest 单测(94个)是其正确性的全部背书,调用方只需要 `loadConstants` 与 `computeParetoFrontier` 两个入口,**不需要也不得了解内部实现**
- **怀疑引擎结果错误时**:在 `packages/apple-value-engine/` 执行 `pnpm test`。测试全绿 → 问题在调用参数或 constants.json 数据侧,回到 SOP 对应步骤排查;测试失败 → 记录失败用例名告知维护者,本次改走文字路径
- **禁止阅读引擎源码、禁止修改引擎**:任何分析流程都不包含"修引擎"这个动作;引擎缺陷不阻塞分析,文字路径永远可用

### 调用方式

计算脚本(.mjs,支持顶层 await)用 `loadEngine()` 加载——路径定位与 CJS 兼容垫片已封装在加载器内,勿手写 import 路径:

```javascript
import { readFileSync } from 'node:fs';
import { loadEngine } from '<技能目录>/scripts/load-engine.mjs';

// 1. 加载引擎(冒烟 PASS 后必然成功)
const { engine } = await loadEngine();
const { loadConstants, computeParetoFrontier } = engine;

// 2. 获取 constants.json 文本(远程获取逻辑见上方"获取与更新机制")
const jsonText = readFileSync('<技能目录>/constants.json', 'utf-8');

// 3. 加载并校验常量(内部完成中文键名 → 英文字段名映射,无需预处理)
const constants = loadConstants(jsonText);

// 4. 调用引擎计算帕累托前沿(替代步骤 4-6 的手动计算)
const result = computeParetoFrontier(constants, {
  category: 'mac-mini',      // 品类
  budget: 5000,              // 预算上限
  holdingYears: [2, 3, 4],   // 候选持有年数
  buyTiming: 'used',         // 'new' | 'used' | 'both'
  performanceFloor: 0.7,     // 性能地板(0-1)
  considerWait: true,        // 是否考虑等新品候选(类型 B/C),默认 true
  macroContext: {            // 宏观状态(可选,缺省时引擎按 'none'/false 处理)
    storageSuperCycleStage: 'ongoing', // 'ongoing'|'peaking'|'easing'|'none'
    hasGlobalPriceHike: true,          // 是否处于全球涨价潮
    analysisMonth: '2026-08',          // 分析月(YYYY-MM)
  },
});

// 5. result.frontier = 前沿非劣方案(按月均成本升序)
//    result.dominated = 被支配方案
//    result.recommendationRange = 用户偏好截取的推荐区间
//    PlanPoint.candidateType: 'A'=现在买 / 'B'=等新品买新品 / 'C'=等新品后买降价老款
//    PlanPoint.predictedPrice=true 表示买入价为预测值(类型 B/C),报告中需标注「预测值」
```

> **macroContext 注入**:宏观状态取自步骤2「宏观扫描」的结果(`_分层扫描框架._L1结果` 与 `_L2判定`)。分析月接近新品发布期(≤ 90 天)且 `releaseConfidence !== 'low'` 时,引擎自动在候选中追加类型 B/C 等待方案,无需手动调用。`considerWait=false` 可显式关闭(仅做现状对比)。

### 引擎路径与文字路径的关系

- **引擎路径(冒烟 PASS 时)**:`loadEngine()` + `loadConstants` + `computeParetoFrontier` → 直接获取前沿结果 → 跳至步骤 7 生成报告
- **文字路径(冒烟 FAIL 或引擎仓库外使用,永不可少)**:按步骤 1-7 逐执行,Agent 自行完成保值率插值、性能满足度、月均成本、帕累托筛选的计算

两条路径使用同一份 constants.json,输出结果一致(引擎单测 fixtures 来自文字路径产出的历史报告)。步骤 1-3(候选方案、宏观扫描、市场价校验)和步骤 7(报告生成)两条路径下均需执行,仅步骤 4-6 可由引擎替代。

### 引擎结果的人工补齐清单(3项)

引擎与 SOP 公式的已知差距,调用引擎后**仍须人工完成并在报告标注**:

1. **三情景加权与类型C失效判定**:引擎按情景A(全额传导)单一口径计算,三情景加权与失效判定须按 [reference/pricing-scenarios.md](reference/pricing-scenarios.md) §3/§5 手动完成
2. **分档差异化锚涨幅**:引擎取品类级单一中位数,分档差异(如 Mac mini 基础档 vs Pro 档)须人工分档计算(同上模块 §5.1)
3. **推算区间敏感性与变体折算**:引擎按 constants 跑分原值计算,不做区间敏感性与变体折算(M5 Pro 15核基础款会被高估约10%),涉及推算/变体跑分的候选须按 [reference/performance-models.md](reference/performance-models.md) §1/§2 人工修正并在报告标注

引擎与 SOP 的历史同步记录见 [CHANGELOG.md](CHANGELOG.md)。引擎对调用方是黑盒,无需了解其内部实现(信任边界见上)。

> **官宣未发售场景(2026-08-29 v4.2 起)**:引擎已直出正确口径——锚定品(与下一代同批发布的机型)自动排除出类型C、S(0) 不再截断于 100%(推算跑分超基准的新芯片性能可 >1)、类型A 非锚定品残值自动施加发布冲击时变调整。此前为修正此口径所写的人工后处理脚本(如 `scripts/mac-mini-postprocess-20260828.mjs`)已降级为历史参考,不再使用。

## 0. 设计原则

1. **以事实为依据**:所有判断从数据出发。宏观因素通过实时扫描发现不预设;规律从 constants.json 统计得出不预设结论;常量按分级校验原则验证,不做无效重复校验
2. **决策范围灵活**:默认聚焦用户关心的单一品类;若用户明确要求跨品类/全品类对比,框架可直接推广,按相同量化指标横向比较
3. **帕累托前沿决策**:候选方案为(机型 × 持有期 × 买入时机)组合,在(月均成本, 持有期平均性能)平面上计算帕累托前沿,前沿上的点即为非劣解。买入时机 ∈ {现在, 新品发布后}。用户偏好(性能地板/预算上限)仅用于在前沿上截取区间,不用于人为设阈值分类
4. **结论先行**:输出先给结论与方案,再给支撑证据与图表说明
5. **成本效益平衡**:常量校验、快照搜索更新遵循"够用就好"原则,在保证决策准确性的前提下节约分析成本
6. **事实落盘与上下文恢复**:从步骤1起,每步的"输出"同步追加写入工作目录 `analysis-facts.md`(引擎冒烟结果、候选清单、校验结论、价格表、计算中间值)。上下文被压缩后**只重读该文件**恢复进度,禁止重读 constants.json 全文或重新执行已完成的步骤

## 1. 输入规范

### 1.1 必需输入
- **目标产品/范围**:单一品类(如"Mac mini"或"iPhone")、多品类对比(如"手机和电脑哪个更值得换")或全品类扫描。表述模糊(如"想换个苹果设备")时用 AskUserQuestion 确认
- **预算区间**:如"3000-5000元"

### 1.2 可选输入
- **预期持有月数**:用户指定固定持有期(如"就用2年")时,跳过多持有期展开,退化为单持有期机型对比。未指定则默认展开 {12, 18, 24, 36, 48, 60} 月,持有期作为决策维度由帕累托前沿筛选
- **使用场景**:轻度办公/开发/视频剪辑/AI推理等(影响性能满足度修正系数)
- **新品/二手偏好**:未指定则两类都分析
- **配置偏好**:芯片代次/内存/存储
- **性能地板**:最低可接受平均性能满足度(如"不低于50%"),用于前沿截取。未设定则在报告中给出三档参考(40%/50%/60%)

### 1.3 输入缺失处理
必需输入缺失时**必须**用 AskUserQuestion 询问,不得假设。典型问题模板:
- "您主要想买哪一类?手机 / 电脑 / mini / 多品类对比 / 其他"
- "预算大致是多少?3000以下 / 3000-6000 / 6000-10000 / 10000以上"
- "打算用几年?(可选,不指定会帮您对比不同持有期的性价比)1年以内 / 1-2年 / 2-3年 / 3年以上 / 不确定"

## 2. 执行步骤(场景路由 + 7步标准流程)

**查询纪律**:以下步骤中所有"查 constants.json"一律指用 `scripts/query-constants.mjs` 按键路径取值(键名不明先 `--list`/`--search`),禁止整读 constants.json;各步输出同步落盘 `analysis-facts.md`(设计原则6)。

### 步骤0:场景路由(每次分析开始时判定)

主流程只含通用规则,场景细则在 reference 模块。以下条件命中时读对应模块再继续(同一次分析可能命中多条):

| # | 判定条件(判定时点) | 动作 |
|---|---|---|
| R1 | 新品已官宣定价,锚涨幅(官宣价 vs 老款现行官方价)> +5% 或 < −5%(步骤1列候选时) | 读 pricing-scenarios.md:双因子模型、三情景、失效判定、残值分母切换 |
| R2 | 候选含已官宣未发售新品,其跑分为推算值(constants 芯片条目带"_实测说明"推算标注)(步骤1列候选时) | 读 performance-models.md:推算口径、区间敏感性、变体折算 |
| R3 | 步骤3判定快照需黄色/红色更新,或采样疑似污染 | 读 market-sampling.md:数据源优先级、筛选与置信度规则 |
| R4 | 进入步骤7报告生成 | 读 report-design.md:图表规范、视觉纪律、报告结构 |
| R5 | 平价换代(锚涨幅 −5%~+5%)或新品未官宣 | 不加载场景模块,走主流程既有类型B/C逻辑 |
| R6 | 多品类对比 / 用户指定固定持有期 | 主流程内分支(步骤1/步骤6),无需模块 |

R1 与 R2 常同窗发生(官宣未发售):R1 管该窗口的**价格**不稳定,R2 管**性能**数据不确定,两者互补。

**引擎冒烟(每次分析开始执行)**:运行 `node <技能目录>/scripts/engine-smoke.mjs`,把结果(含引擎路径或失败原因)记入 `analysis-facts.md`。PASS → 步骤4-6 走引擎路径;FAIL → 走文字路径,**不诊断引擎**(详见「引擎调用」)。冒烟失败不阻塞分析,继续步骤1。

### 步骤1:确定分析范围与候选方案

**操作**:
1. 解析分析范围:单一品类映射到 constants.json 品类键(如"Mac mini"→"Mac_mini");多品类/全品类对每个品类分别列出候选机型,后续独立完成计算再横向比较
2. 列出候选机型(各代芯片 × 主流配置组合),计算当前机龄:查 constants.json "产品发布日期",代入 `机龄(月) = (分析年 − 发布年)×12 + (分析月 − 发布月)`;未收录则 WebSearch "{产品名} 发布日期" 补充
3. **生成候选方案**(机型 × 持有期;持有期候选集默认 {12, 18, 24, 36, 48, 60} 月,用户指定固定持有期则只生成该持有期):
   - **类型A(现在买)**:买入价取步骤3快照/搜索的当前市场价
   - **类型B(等新品后买新品)/ 类型C(等新品后买降价老款)**:仅当步骤2判定距新品发布 ≤ 90天(主动触发)或用户明确要求(被动触发)时生成;constants.json "苹果产品发布节奏"无"下一次预计"字段则不生成。买入价预测、等待月数计算、失效判定见 [pricing-scenarios.md](reference/pricing-scenarios.md)(已官宣涨价/降价发布须先经路由 R1)
   - 类型B/C的持有期候选集与类型A相同
4. **硬约束排除**:< 6月持有期且为二手买入 → 排除(开箱效应期贬值最快,不划算)
5. **系统支持期风险标注**(不排除,仅标注):持有期末超出品类系统支持月数(macOS约72月/iOS约60月/watchOS约48月,见 constants.json "苹果产品发布节奏")→ 标注"⚠ 持有期末超出系统支持期X月"并列出风险(无法获取安全更新、新软件可能不兼容);剩余<12月 → 标注"⚠ 接近系统支持尾声",提示卖出时机
6. 候选清单含 constants.json 未覆盖机型 → 扩展流程(§6)

**术语说明**:"机龄"与"发布后月数"含义相同,统一使用"机龄(月)"

**输出**:候选方案清单,每个方案标注(机型, 配置, 当前机龄, 持有期, 卖出时机龄, 类型A/B/C)

### 步骤2:宏观因素扫描与常量分级校验

**目的**:发现当前环境影响因素,按分级原则校验常量,平衡准确性与分析成本。

**常量分级校验规则**(三级):
- **绿色(免检)**:常量最后更新在30天内,且期间无苹果新品发布、无重大行业价格事件 → 直接使用,无需校验
- **黄色(轻校验)**:常量最后更新在30-90天内,或期间有小型事件 → 执行1-2条搜索交叉验证保值率/价格趋势,无明显偏差则直接使用
- **红色(全校验)**:常量最后更新超过90天,或期间有重大事件(新品发布、官方调价、存储价格异动超过20%) → 完整执行3条宏观搜索+保值率校验

**操作**:
1. **判定常量校验级别**:根据 constants.json 的 `last_updated` 日期和近期事件,判定绿/黄/红三级
2. **分层宏观扫描**(按 constants.json "宏观因素扩展模型_v3.8" 框架执行):
   - **L1_必扫层**(每次分析执行;红色级别执行3条,黄色执行1-2条,绿色跳过):
     - `苹果 涨价 调价 {当前年份} 最新` — 是否有官方涨价事件
     - `DRAM NAND 存储 价格 {当前年份} TrendForce` — 是否有存储芯片价格异动
     - `苹果 新品 发布 {当前年份} 路线图` — 是否有临近的新品发布
   - **L2_存储超级周期层**(L1检测到存储事件时触发):搜索"TrendForce 内存 见顶 预测"、"DRAM NAND 缓解 2027 2028"、"AI HBM 挤压 消费级 产能",判定周期阶段 ∈ {进行中, 见顶中, 缓解, 无事件}
   - **L3_BOM成本层**(L1/L2涉及具体品类时触发):搜索"{品类} BOM 成本 {当前年份} TechInsights"、"{具体新品} 售价 涨幅 分析师",更新 constants.json "新品发布对老款冲击._新品价格预测模型_v3.8._分品类预测涨幅表"
   - **L4_产能与缺货层**(涉及Mac Studio/Mac Pro等高延迟品类时触发):搜索"{品类} 缺货 排队 交付延迟 {当前年份}",更新 constants.json "苹果产品发布节奏._缺货等待期模型_v3.8"
3. **判断影响因素**:
   - **等待新品触发判定**:查 constants.json "苹果产品发布节奏"对应品类的"下一次预计"字段,计算距分析日期的月数。≤3月 → 主动触发(步骤1生成类型B/C候选);>3月 → 被动触发(仅用户明确要求时生成);无"下一次预计" → 不触发
   - **发布时间预测校验**:对涉及类型B/C候选的品类,执行 constants.json "苹果产品发布节奏._发布时间预测校验_v3.8" 校验机制。若搜索结果偏离预测≥1季度,在报告中标注"⚠️ 发布时间预测偏差≥1季度,类型B/C方案置信度降级"
4. **常量校验结论**:绿色 → 记录"常量近期已校验,无需更新";黄色 → 记录校验结果,有偏差则标记;红色 → 对比搜索数据,实测保值率偏离曲线>15%标记需更新,出现新芯片标记需补充,超过12个月标记需年度更新
5. **影响传导判断与机制激活**(根据L2判定的周期阶段):
   - **存储超级周期_进行中** → ①启用"缺货等待期模型.宏观产能延迟"因子=2.0;②启用"新品价格预测模型",对所有未发布新品使用预测涨幅中位数;③对"新品发布对老款冲击"均值按价格传导因子表向下修正;④报告中标注"⚠️ 当前处于存储超级周期,新品价格预测/冲击调整/缺货延迟已启用宏观修正"
   - **存储超级周期_见顶中** → 因子=1.5,预测涨幅中位数减半,冲击修正幅度减半
   - **存储超级周期_缓解/无事件** → 全部使用默认值,不启用宏观修正

**输出**:校验级别 + 宏观因素清单(分层) + 常量校验结论 + 调整方案 + **等待新品触发判定** + **周期阶段判定与激活的机制清单**

### 步骤3:校验市场价快照并按需更新

**核心机制**:constants.json "实时市场价快照"已存储已搜索的真实交易渠道价格。本步骤**优先校验快照是否可用**,仅在必要时按分级规则做最小化搜索更新,避免每次分析全量搜索。

#### 3.0 快照分级校验规则

查 constants.json "实时市场价快照.snapshot_date" 与 "_快照分级使用规则",根据分析日期与快照日期的间隔判定级别:

- **≤14天(绿色免更新)**:直接使用快照价格,仅对快照中缺失的候选机型做补充搜索
- **15-30天(黄色轻校验)**:对已有机型做1条交叉验证(京东自营当前价),偏差<5%继续使用快照;偏差≥5%或近14天有苹果官方调价/新品发布事件则对受影响机型重新搜索
- **>30天 或 近30天有苹果官方调价/新品发布(红色全更新)**:全量重新搜索,并回写更新本快照

#### 3.1 执行

- 命中黄色/红色 → 触发路由 R3,按 [market-sampling.md](reference/market-sampling.md) 的数据源优先级(官网直采→可信二手资料→browser-use→兜底)、价格筛选规则(含**同代配置价格倒挂校验**)、置信度标注与快照回写执行
- **残值分母(当前同品类新品价)** = 该品类当前在售最新一代**同芯片级别**产品的官方售价(不是该机型自身的原始发布价),完整定义与取值方法见 market-sampling.md §2。优先查快照对应品类"官方价"字段,无则 WebFetch 苹果官网
- 若用户提供具体闲鱼/爱回收/京东链接或截图,优先使用用户提供的数据(置信度可升至高)

**输出**:各候选机型的价格表,每个价格标注置信度等级和搜索来源URL

### 步骤4:计算持有期平均性能满足度

**公式**(来自 constants.json):
```
S(0) = 芯片性能系数 × 内存权重 × 存储权重 × 100%
芯片性能系数 = 该芯片多核跑分 / 品类基准芯片多核跑分

持有期衰减(基准芯片更新导致相对性能下降):
S(t) = S(0) / (1 + r)^(t/12)
S̄(N) = [S(0) + S(N)] / 2         持有期平均(线性近似)

r 取值(按芯片系列,M系列 r=0.16 / A系列 r=0.15,依据与波动说明见
reference/performance-models.md §4):
  M系列(M1/M2/.../M6): r = 0.16
  A系列(A14/A15/.../A19): r = 0.15
```

**操作**:
1. 查 constants.json "芯片性能跑分"得该芯片多核跑分;查"性能满足度计算公式.品类基准芯片"得基准芯片及跑分——**基准保留最后一个实测旗舰**(口径规则与例外见 performance-models.md §1.1)
2. 按品类选内存权重/存储权重子表,代入静态公式得 S(0)
3. 对每个候选持有期 N,计算 S(N) 和 S̄(N)
4. **类型B新品性能预测**:按新品官宣状态分两支:
   - **未官宣**:新品为新的基准芯片,S(0)=100%;新品跑分预测 = 当前最新旗舰跑分 × (1+r)^(发布周期月/12);S̄(N) = [100% + 100%/(1+r)^(N/12)] / 2
   - **已官宣未发售**:触发路由 R2,按 [performance-models.md](reference/performance-models.md) 推算口径处理(新芯片系数 = 推算跑分 ÷ 实测基准,允许 >100%)并做区间敏感性;含代际跃升调整
5. **类型C性能**:等新品买降价老款,S(0)和S̄(N)与类型A相同——衰减模型已通过r因子覆盖持有期内的基准更新
6. 场景修正:轻度办公 ×1.2(上限100%);专业工作流 ×0.9。修正应用于 S̄(N)

数值演算示例见 performance-models.md §5;长持有期(>36月)衰减预测置信度降低,报告中标注。

**输出**:各候选方案的持有期平均性能满足度 S̄(N)%,标注S(0)和S(N)

### 步骤5:计算月均成本(含持有期预期维修成本)

**公式**(来自 constants.json):
```
月均成本 = (买入价 - 预期卖出残值 + 持有期预期维修成本) / 持有月数
预期卖出残值 = 调整后保值率 × 当前同品类新品价(残值分母,定义见步骤3.1)

预期维修成本 = 预期电池更换费用 + 预期故障维修费用
预期电池更换费用 = floor(持有月数 / 电池寿命周期) × 单次电池更换费用
预期故障维修费用 = 持有年数 × 年均故障维修费用(见constants.json)
```

**保值率查表方法**:
- 卖出时机龄恰好在曲线上 → 直接取值
- **两点之间线性插值**:`保值率 = 保值率[i] + (保值率[i+1] - 保值率[i]) × (目标月数 - 月数[i]) / (月数[i+1] - 月数[i])`
- **曲线末点(通常60月)后外推**——指数衰减:`R(t) = floor + (R(last) − floor) × 0.5^((t − last月数) / half_life_months)`,floor与半衰期查各品类曲线 `_floor`(默认3)与`_half_life_months`(默认24)。线性外推在96-120月区间会产生负残值,故弃用
- **外推无月数上限**:超出系统支持期时按指数衰减继续外推,但报告中必须标注"⚠ 超出系统支持期X月"
- **保底**:保值率不低于3%

**操作**(对每个候选方案,即每个机型×持有期组合):
1. **买入价**:
   - 类型A:当前快照价
   - 类型B:已官宣 → 官宣价;未官宣且宏观触发"新品价格预测模型" → 当前同档老款官方价 × (1+预测涨幅中位数);未触发 → 同档同价假设。完整规则见 pricing-scenarios.md §4
   - 类型C:双因子公式(当前老款市场价 × (1+锚涨幅) × (1−调整后冲击幅度×冲击时变因子)),**涨价发布时须先做三情景加权与失效判定**——权威定义见 pricing-scenarios.md §3
2. **持有期末机龄**:类型A = 当前机龄 + 持有月数;类型B ≈ 持有月数(新品买入时机龄≈0);类型C = 当前机龄 + 等待月数(含缺货延迟) + 持有月数
3. 查表得到原始保值率
4. **新品发布冲击调整**(仅类型A,若持有期内有新品发布):冲击后保值率 = 原始保值率 × (1 - 调整后冲击幅度 × 残值调整时变因子),残值调整时变因子查 constants.json "新品发布对老款冲击._冲击时变曲线_v3.8"(1月内=0.95,3月内=0.85,6月内=0.60,12月内=0.30,12月后=0.10),调整后冲击幅度按"._宏观因子调整_v3.8"修正。类型B/C不施加此调整——类型B买入的就是新品;类型C的冲击已体现在买入价中
5. **宏观因素调整**(若适用):`调整后保值率 = 原始保值率 × (1 - 预期价格回落幅度)`,其中"预期价格回落幅度" = 涨价幅度 × 预判消退比例
6. 若同时存在新品冲击和宏观因素,乘法叠加
7. **残值分母**:类型A持有期内新品官宣涨价发布时,分母切换为新品官宣价,锚定与冲击两股力量乘法叠加(勿只计冲击项);类型B/C的分母规则(预测价/官宣价/快照价三种情形)见 pricing-scenarios.md §6
8. 计算持有期预期维修成本(查 constants.json "持有期预期维修成本"参数)
9. 代入月均成本公式
10. **等待期机会成本**(可选):若用户在步骤1提供了"无设备可用的替代成本/月"(如租机费用或降级使用损失),类型B/C的月均成本 = 原月均成本 + 等待月数 × 替代成本 / 持有月数

**输出**:各候选方案月均成本,标注买入价、调整后残值、维修成本、持有月数、各项调整依据,以及激活的宏观机制清单

### 步骤6:帕累托前沿分析与决策

**核心思想**:所有候选方案在(月均成本, 持有期平均性能)平面上构成散点,帕累托前沿(非劣解集)即为不存在"成本更低同时性能更高"的其他方案的集合。前沿上的点都是合理选择——取决于用户偏好。类型A/B/C方案在同一前沿上比较。

**操作**:
1. **构建决策空间**:所有通过硬约束筛选的候选方案,以(月均成本, S̄(N))为坐标画散点
2. **计算帕累托前沿**:方案A被方案B支配,当且仅当 B的月均成本 ≤ A 且 B的S̄(N) ≥ A,且至少一个严格不等;前沿 = 不被任何其他方案支配的方案集合
3. **剔除被支配点**:被支配的方案直接排除,不进入推荐
4. **前沿上截取推荐区间**(根据用户偏好):
   - **用户指定性能地板**(如"平均性能不低于50%")→ 在前沿上保留 S̄(N) ≥ 性能地板的段,推荐该段上成本最低的1-2个方案
   - **用户指定预算上限** → 在前沿上保留月均成本对应的年化支出 ≤ 预算/持有年数的段
   - **均未指定** → 给出前沿的三档参考:经济档(最左端,成本最低性能也最低)、均衡档(中段)、性能档(最右端,性能最高成本也最高),询问用户偏好后确定最终推荐
   - **固定持有期退化**:用户指定固定持有期时每个机型仅一个点,前沿退化为该持有期下的机型排序
5. **标注不确定性**:长持有期(>36月)的保值率为外推,性能衰减为假设 → 前沿右下段置信度低,标注"预测不确定性高";短持有期(<12月)数据点少,置信度中等;12-36月区间的候选方案置信度最高

**超预算处理**:若前沿上所有方案均超预算,明确告知,在前沿下方(被支配区)找最接近预算的方案,标注"虽非前沿最优,但在预算约束下的最佳折中"。

**多品类/全品类决策**:
1. 每个品类先独立完成候选方案生成、价格搜索/快照校验、计算、帕累托前沿分析,得到各品类前沿
2. 将各品类前沿上的方案放在一起,在统一的(月均成本, S̄(N))平面上再算一次跨品类帕累托前沿
3. 明确说明跨品类比较的局限性(场景差异大,量化指标仅供参考)
4. 最终推荐结合用户使用场景给出定性建议

**输出**:帕累托前沿图 + 前沿方案表 + 推荐区间 + 被支配点剔除清单

### 步骤7:输出报告(结论先行)

报告结构、图表规范与视觉纪律的完整定义见 [report-design.md](reference/report-design.md)(进入本步骤前必读);所有可复制代码(CSS token、ECharts 模板)的唯一权威源为 constants.json `design_tokens` 字段。

结构概要:
- **第一部分:结论与推荐方案**——一句话结论(买什么、怎么买、持有多久)、推荐方案表(型号/配置/买入时机/买入价/持有期/月均成本/平均性能/推荐理由)、前沿备选清单、等待方案提示(类型B/C标注等待月数与"预测值",提示等待期机会成本)
- **第二部分:支撑证据**——帕累托前沿图、完整候选方案计算表(含被支配点及剔除原因)、宏观因素分析、常量校验结论、维修成本明细
- **第三部分:图表说明**——前沿图阅读方法、各点含义、不确定性标注说明
- **第四部分:更新提示**——触发重新分析的条件、下次建议分析时间

**输出**:单个自包含 HTML 文件,输出到当前项目工作目录,文件名 `YYYY-MM-DD-苹果产品购买决策报告.html`。

## 3. 规律提炼方法(以事实为依据)

- **不预设任何规律结论**:所有规律必须从 constants.json 数据中统计得出
- 贬值速度统计方法:`斜率_i = (保值率[i+1] - 保值率[i]) / (月数[i+1] - 月数[i])`
- 规律表述规范:基于数据统计描述,不使用预设结论式表述;标注统计样本来源

## 4. 数据质量保证

### 4.1 常量置信区间
- 保值率数据置信区间 ±5-10%
- 代际跨越可能导致老款额外贬值10-15%
- 偏离曲线超过15%时标注"代际差异"

### 4.2 帕累托分析的不确定性
- 长持有期(>36月):保值率为外推,性能衰减率(M系列16%/A系列15%)为CAGR假设且近期有放缓迹象 → 前沿右下段置信度低
- 短持有期(<12月):数据点少,置信度中等
- 12-36月区间:置信度最高
- 报告中必须标注各候选方案的置信度等级

变量搜索规则与时效性(二手价样本量、优先级、30天时效、年度更新)见 market-sampling.md §6。

## 5. 禁忌清单

1. **不得预设宏观因素**:每次分析前按步骤2级别扫描,不固化"存储涨价"等因素
2. **不得预设规律结论**:规律从 constants.json 数据统计得出
3. **不得凭空给数值**:所有量化指标按公式计算
4. **不得混淆常量与变量**:常量来自 constants.json(含实时市场价快照),变量来自快照外实时搜索
5. **不得假设用户需求**:必需输入缺失时用 AskUserQuestion 询问
6. **不得使用英文缩写时间**:"2027H2"写"2027年下半年"
7. **不得把短期泡沫当长期趋势**
8. **不得先给框架后给结论**:必须结论先行
9. **必须使用中文表达,代码注释也用中文**
10. **保值率曲线年度更新**:按SOP每年1月更新,年中不修改。分析时若发现实测保值率与曲线偏差>10pp,在报告中标注"实测偏差提示"(见constants.json "贬值规律说明")
11. **等待方案价格不得回写快照**:类型B/C买入价均为预测值,不得回写至 constants.json "实时市场价快照"(快照仅记录实际搜索到的真实价格)。新品发布后应重新分析,用真实价格替换预测值
12. **禁止整读 constants.json**:查询一律用 `scripts/query-constants.mjs`(键路径 / --list / --search),整读 1900+ 行文件浪费上下文且易遗漏
13. **禁止阅读或修改引擎源码**:引擎是黑盒,信任边界与例外流程见「引擎调用」;引擎冒烟失败或疑似计算有错时走文字路径 / 跑 `pnpm test`,不诊断、不读源码、不修复

**详细规则索引**(不重复展开):
- 数据源/置信度/5项标准/挂单价非实付/倒挂校验 → market-sampling.md
- 系统支持期不作硬排除(仅标注风险) → 步骤1.5
- 持有期是决策维度、帕累托前沿不可替代 → 步骤1.3 与步骤6
- 每个变量必须标注数据来源、搜索时间、置信度 → market-sampling.md §3

## 6. 扩展流程:处理新品类/新芯片

当遇到 constants.json 未覆盖的产品或芯片时:
1. 识别新芯片/新品类
2. 搜索至少6个月历史二手价数据
3. 拟合保值率曲线(不足时参考相近品类)
4. 搜索Geekbench跑分
5. 更新 constants.json,版本号同步递增
