# 苹果产品价值分析与购买决策 SOP

## 何时调用本技能 (When to Invoke)

**当出现以下任一情况时,必须调用本技能(而非直接回答或单纯联网搜索):**

- 用户想购买苹果设备(Mac / iPhone / iPad / Apple Watch / AirPods / Vision Pro 等),需要决策"买哪款、买新品还是二手、用几年划算"
- 用户想对比苹果产品**各代机型**或**不同持有期**的性价比 / 月均成本 / 保值率
- 用户询问苹果产品的**保值率、残值、贬值速度**(如"M2 现在还值多少钱""还能撑几年")
- 用户在多款苹果设备间纠结"**先换哪个 / 哪个更值得换**"(多品类对比)
- 用户给出**预算 + 品类**,要求推荐最划算的购买方案(如"5000 预算买 Mac mini,怎么买最值")
- 用户明确要求基于数据做**购买决策报告**或**性价比量化分析**
- 用户想**预估涨价 / 新品发布对二手市场的影响**(如"这次涨价后二手价会怎么走""老款现在卖还是等发售后卖""等新品发布再买旧款能便宜多少")

### 触发示例(用户原话)

- "想买个 Mac mini,预算 5000 以内,不知道用几年划算"
- "iPhone 15 和 16 哪个值得买?用两年哪个省"
- "MacBook Air M2 二手现在入手合适吗"
- "手机和电脑哪个该先换"
- "帮我分析下苹果产品保值率,做个购买决策报告"
- "M4 新品国补后还值得买吗,对比二手"

### 不应调用的情况

- 仅查询苹果产品**参数 / 跑分 / 发布日期**(直接 WebSearch 即可,无需全流程分析)
- **非苹果产品**(本技能常量库仅覆盖苹果全系,不适用安卓/Windows 设备)
- 仅比较**电商平台当前价格**、无持有期 / 残值 / 性价比分析需求
- 用户只想要一段口述建议,明确表示不需要报告或量化计算

## 本技能做什么 (What This Skill Does)

基于 `constants.json` 常量数据库(保值率曲线、芯片跑分、维修成本、实时市场价快照等,获取方式见下方"依赖文件"章节)与按需校验更新的市场价快照,执行 **7 步标准流程**:确定候选方案 → 宏观因素扫描与常量分级校验 → 校验市场价快照并按需更新 → 计算持有期平均性能满足度 → 计算月均成本(含预期维修成本) → 帕累托前沿分析 → 结论先行的 HTML 报告。核心输出为(月均成本, 持有期平均性能)平面上的**帕累托前沿**,前沿上的非劣解即为合理购买方案。

## 依赖文件

- **`constants.json`**:本技能的唯一常量数据源,含保值率曲线、芯片性能跑分、内存/存储权重、发布节奏、维修成本、实时市场价快照、等待新品发布候选方案、报告视觉与图表实现(`design_tokens` 字段)等。**constants.json 的版本号可能高于 SKILL.md 的 SOP 版本**——SOP 版本追踪方法论(流程/公式/规则),constants.json 版本追踪数据(保值率/跑分/快照),两者独立演进。只要 SOP 定义的字段结构存在于 constants.json 中即可正常工作,不要求版本号一致(当前 SOP 为 v4.1)。
- 文中所有"查 constants.json / 见 constants.json"均指本文件(可能位于 SKILL.md 同目录,也可能由远程获取后缓存至同目录)。**SKILL.md 不依赖 constants.json 之外的任何外部文件**。
- **实时市场价快照**:存储已搜索的真实交易渠道价格(苹果官网/京东自营/闲鱼/爱回收/京东拍拍)及符合5项标准的可信二手资料价格。下次分析时优先校验本快照是否需要更新,避免每次全量搜索。快照分级使用规则见 constants.json "实时市场价快照._快照分级使用规则"

**获取规则**(每次技能被调用时,在步骤1之前执行):
1. **检查本地文件**:检查 SKILL.md 同目录下是否存在 `constants.json`
2. **本地不存在**:从远程获取 constants.json,保存到 SKILL.md 同目录下,供本次及后续分析使用
3. **本地存在**:读取 `metadata.last_updated` 日期(而非版本号),判断数据是否过期:
   - **未过期**(距今 ≤ 7 天):直接使用本地文件,跳过网络获取
   - **已过期**(距今 > 7 天):从远程获取最新版,覆盖本地文件。覆盖前提示用户"constants.json 数据已过期(上次更新: YYYY-MM-DD),正在从远程获取最新版"
4. **远程获取失败时的双源容错**:
   - 先尝试 Gitee 主源;若失败(超时/不可达),自动回退到 GitHub 备份源
   - **两个源均不可达**:
     - 若本地有旧版文件 → 使用旧版,在报告中标注"⚠️ 常量数据可能过期(上次更新: YYYY-MM-DD,远程获取失败),市场价快照等时效性数据可能不准确,建议稍后重试或手动更新"
     - 若本地无文件 → 提示用户手动从上述任一远程地址下载 constants.json 并放置于 SKILL.md 同目录,终止执行

**关键原则**:获取最新版**不依赖版本号比对**。远程 constants.json 可能每周更新(市场价快照回写、跑分更新等),其版本号会高于用户本地 SKILL.md 的 SOP 版本,这是正常现象——SOP(方法论)与 constants.json(数据)独立演进。判断是否需要更新的唯一依据是 `metadata.last_updated` 日期,而非版本号。

**获取方法**:使用 WebFetch 获取上述远程地址的 JSON 内容,解析后保存为同目录下的 `constants.json`。优先请求 Gitee 地址,失败时回退 GitHub 地址。

**数据维护**:constants.json 的更新(保值率曲线年度更新、芯片跑分更新、市场价快照回写等)统一在远程仓库进行,**更新节奏约为每周一次**(主要为市场价快照回写,大版本含保值率/跑分更新频率更低)。分析过程中本地回写的市场价快照仅用于本次分析,不自动推送至远程——远程仓库的 constants.json 由维护者定期合并各分析节点的快照更新。用户本地 SKILL.md 的 SOP 版本不需要跟随 constants.json 版本升级,只要 SOP 定义的字段结构在 constants.json 中存在即可正常工作。**Gitee 与 GitHub 两个仓库内容保持同步**(同步策略见仓库 README.md "双仓库同步"章节)。

## 引擎调用(优先路径)

本技能的帕累托前沿算法已抽离为独立 TypeScript 引擎包 `apple-value-engine`(位于仓库 `packages/apple-value-engine/`)。**当 Agent 运行环境支持 npm/Node.js 时,优先调用引擎执行计算,跳过下文 SOP 步骤 4-6 的手动计算**。

### 调用方式

```typescript
import { loadConstants, computeParetoFrontier } from 'apple-value-engine';

// 1. 获取 constants.json(远程获取逻辑不变,见上方"获取与更新机制")
const jsonText = await fetchConstantsJson(); // 现有远程获取逻辑

// 2. 加载并校验常量
const constants = loadConstants(jsonText);

// 3. 调用引擎计算帕累托前沿(替代 SOP 步骤 4-6 的手动计算)
const result = computeParetoFrontier(constants, {
  category: 'mac-mini',      // 品类
  budget: 5000,              // 预算上限
  holdingYears: [2, 3, 4],   // 候选持有年数
  buyTiming: 'used',         // 'new' | 'used' | 'both'
  performanceFloor: 0.7,     // 性能地板(0-1)
  considerWait: true,        // 是否考虑 v3.8 等新品候选(类型 B/C),默认 true
  macroContext: {            // 宏观状态(可选,缺省时引擎按 'none'/false 处理)
    storageSuperCycleStage: 'ongoing', // 'ongoing'|'peaking'|'easing'|'none'
    hasGlobalPriceHike: true,          // 是否处于全球涨价潮
    analysisMonth: '2026-08',          // 分析月(YYYY-MM)
  },
});

// 4. result.frontier = 前沿非劣方案(按月均成本升序)
//    result.dominated = 被支配方案
//    result.recommendationRange = 用户偏好截取的推荐区间
//    PlanPoint.candidateType: 'A'=现在买 / 'B'=等新品买新品 / 'C'=等新品后买降价老款
//    PlanPoint.predictedPrice=true 表示买入价为预测值(类型 B/C),报告中需标注「预测值」
```

> **macroContext 注入说明**:宏观状态取自 SOP 步骤 2「宏观扫描」的结果(`_分层扫描框架._L1结果` 与 `_L2判定`)。分析月接近新品发布期(≤ 90 天)且 `releaseConfidence !== 'low'` 时,引擎自动在候选中追加类型 B/C 等待方案,无需手动调用。`considerWait=false` 可显式关闭该机制(仅做现状对比)。

> **v4.1 限制(引擎未同步)**:引擎的 `predictDiscountedOldPrice` 仍为 v3.8 公式(无锚定项),且 `hasHikeOccurred` 识别仅匹配"已发生/已涨价",不识别"已官宣"状态(官宣后快照官方价已是新品价,再乘预测涨幅会重复计算)。涨价发布场景下**优先走 SOP 文字路径**:按 §9.4 手动计算类型B/C买入价(类型B直接用官宣价),或设 `considerWait=false` 关闭引擎的等待候选生成后,把 §9.4 手算结果并入报告。引擎同步 v4.1 为待办事项。性能侧:引擎按 constants 跑分原值计算(基准随 constants 口径为实测 M5,新芯片系数会 >100%),但**不做** §9.5 的推算区间敏感性与变体折算(M5 Pro 15核基础款会被高估约10%),涉及推算/变体跑分的候选须按 §9.5 人工修正并在报告标注

### 引擎路径与 SOP 文字路径的关系

- **引擎路径(优先)**:Agent 环境支持 npm → `loadConstants` + `computeParetoFrontier` → 直接获取前沿结果 → 跳至 SOP 步骤 7 生成报告
- **文字路径(回退)**:Agent 环境不支持 npm → 按下文 SOP 步骤 1-7 逐执行,Agent 自行执行保值率插值、性能满足度、月均成本、帕累托筛选的计算

两条路径使用同一份 constants.json,输出结果一致(引擎单测 fixtures 来自 SOP 路径产出的历史报告)。SOP 步骤 1-3(候选方案确定、宏观扫描、市场价校验)和步骤 7(报告生成)在两条路径下均需执行,仅步骤 4-6 可由引擎替代。

### constants.json 兼容性

引擎的 `loadConstants()` 接收原始 JSON 文本,内部完成中文键名 → 英文字段名的映射。远程获取的 constants.json 无需任何预处理,直接传入即可。现有远程获取逻辑(双源容错、7 天过期判断)完全不变。

## 0. 设计原则

1. **以事实为依据**:所有判断从数据出发。宏观因素通过实时扫描发现不预设;规律从 constants.json 统计得出不预设结论;常量按分级校验原则验证,不做无效重复校验
2. **决策范围灵活**:默认聚焦用户关心的单一品类;若用户明确要求跨品类/全品类对比,框架可直接推广,按相同量化指标横向比较
3. **帕累托前沿决策**:候选方案为(机型 × 持有期 × 买入时机)组合,在(月均成本, 持有期平均性能)平面上计算帕累托前沿,前沿上的点即为非劣解。买入时机 ∈ {现在, 新品发布后}。用户偏好(性能地板/预算上限)仅用于在前沿上截取区间,不用于人为设阈值分类
4. **结论先行**:输出先给结论与方案,再给支撑证据与图表说明
5. **成本效益平衡**:常量校验、快照搜索更新遵循"够用就好"原则,在保证决策准确性的前提下节约分析成本

## 1. 输入规范

### 1.1 必需输入
- **目标产品/范围**:用户想分析的范围。可以是单一品类(如"Mac mini"或"iPhone"),也可以是多品类对比(如"手机和电脑哪个更值得换")或全品类扫描。若用户表述模糊(如"想换个苹果设备"),用 AskUserQuestion 确认范围
- **预算区间**:如"3000-5000元"

### 1.2 可选输入
- **预期持有月数**:用户可指定固定持有期(如"就用2年"),此时跳过多持有期展开,退化为单持有期机型对比。未指定则默认展开多持有期分析(12/18/24/36/48/60月),持有期作为决策维度由帕累托前沿筛选
- **使用场景**:轻度办公/开发/视频剪辑/AI推理等(影响性能满足度修正系数)
- **新品/二手偏好**:未指定则两类都分析
- **配置偏好**:芯片代次/内存/存储
- **性能地板**:用户可设定最低可接受的平均性能满足度(如"不低于50%"),用于在前沿上截取推荐区间。未设定则在报告中给出三档参考(40%/50%/60%)供选择

### 1.3 输入缺失处理
必需输入缺失时**必须**用 AskUserQuestion 询问,不得假设。典型问题模板:
- "您主要想买哪一类?手机 / 电脑 / mini / 多品类对比 / 其他"
- "预算大致是多少?3000以下 / 3000-6000 / 6000-10000 / 10000以上"
- "打算用几年?(可选,不指定会帮您对比不同持有期的性价比)1年以内 / 1-2年 / 2-3年 / 3年以上 / 不确定"

## 2. 执行步骤(7步标准流程)

### 步骤1:确定分析范围与候选方案

**操作**:
1. 从用户输入解析分析范围:
   - **单一品类**:映射到 constants.json 的单个品类键(如"Mac mini"→"Mac_mini"),列出该品类下候选机型
   - **多品类/全品类**:对每个涉及品类分别列出候选机型,后续每个品类独立完成计算后再横向比较
2. 列出各品类下的候选机型(各代芯片 × 主流配置组合)
3. 计算各候选机型的当前机龄(发布后月数):查 constants.json "产品发布日期",代入公式 `机龄(月) = (分析日期年 - 发布年) × 12 + (分析日期月 - 发布月)`。若未收录,WebSearch搜索"{产品名} 发布日期"补充
4. **生成候选方案**:对每个候选机型 × 每个持有期生成候选方案。持有期候选集默认 {12, 18, 24, 36, 48, 60} 月。若用户指定了固定持有期,则只生成该持有期的候选方案
   - **类型A(现有):现在买** — 买入价取步骤3快照/搜索的当前市场价
   - **类型B:等新品后买新品** — 仅当步骤2检测到距新品发布 ≤ 90天(主动触发),或用户明确要求(被动触发)时生成。
     - **买入价预测**(v3.8更新):若步骤2宏观扫描触发"新品价格预测模型"(存储超级周期/全线涨价事件),买入价 = 当前同档老款官方价 × (1 + 预测涨幅中位数),查 constants.json "新品发布对老款冲击._新品价格预测模型_v3.8._分品类预测涨幅表";未触发时回退至"同档同价假设"
     - **等待月数计算**(v3.8更新):等待月数 = max(0, (预计发布年-分析年)×12 + (预计发布月-分析月)) + 上市到货延迟(月)。延迟查 constants.json "苹果产品发布节奏._缺货等待期模型_v3.8",若宏观扫描检测到存储超级周期_进行中,延迟×宏观产能因子(默认2.0)
   - **类型C:等新品后买降价老款** — 触发条件同类型B。
     - **买入价预测**(v4.1更新):买入价 = 当前市场价 × (1 + 锚涨幅) × (1 - 调整后冲击幅度 × 冲击时变因子)。**锚涨幅** = (新品官宣价 - 老款现行官方价) / 老款现行官方价——对比的是老款**现行官方价而非首发价**;新品未官宣定价时锚涨幅 = 0,公式退化为 v3.8 形式。调整后冲击幅度 = 历史均值 × (1 + 价格传导因子),传导因子由锚涨幅查 constants.json "新品发布对老款冲击._宏观因子调整_v3.8._价格传导因子表";未触发宏观事件时使用原始均值。涨价发布(锚涨幅 > 5%)的完整三情景预估见 §9.4
     - **失效判定**(v4.1新增):涨价发布时,若三情景加权买入价 ≥ 当前市场价,"等降价捡漏"逻辑失效——不生成类型C候选,或生成但在报告标注"⚠ 涨价发布,预估买入价不低于当前价,等待无收益"(判定方法见 §9.4)
     - **冲击时变因子**(v3.8更新):买入时距新品发布的月数对应的"买入价下降因子"(查 constants.json "新品发布对老款冲击._冲击时变曲线_v3.8"),1月内=1.0,3月内=0.95,6月内=0.80,12月内=0.50,12月后=0.20
     - 买入时机龄 = 当前机龄 + 等待月数(含缺货延迟)
   - 类型B/C的持有期候选集与类型A相同。若无新品发布预期(constants.json "苹果产品发布节奏"无"下一次预计"字段),则不生成等待候选方案
5. **硬约束排除**(以下方案不进入后续分析):
   - **开箱效应期**:持有期 < 6月 且为二手买入 → 排除(贬值最快区间不划算)
6. **系统支持期风险标注**(不排除,仅标注):
   - 计算持有期末是否超出该品类系统支持月数(见 constants.json "苹果产品发布节奏",macOS约72月/iOS约60月/watchOS约48月等)
   - **超出支持期**:标注"⚠ 持有期末超出系统支持期X月",列出具体风险(无法获取安全更新、新软件可能不兼容),但**不排除该方案**——做这种详细分析的买家通常对系统不支持有较高容忍度(如运行旧版macOS、安装Linux、特定软件不依赖最新系统等)
   - **接近支持尾声**(剩余<12月):标注"⚠ 接近系统支持尾声",提示卖出时机选择
7. 若候选清单中包含 constants.json 未覆盖的机型 → 进入扩展流程(第7节)

**术语说明**:"机龄"与"发布后月数"含义相同,统一使用"机龄(月)"

**输出**:候选方案清单,每个方案标注(机型, 配置, 当前机龄, 持有期, 卖出时机龄)

### 步骤2:宏观因素扫描与常量分级校验

**目的**:发现当前环境影响因素,按分级原则校验常量,平衡准确性与分析成本。

**常量分级校验规则**(三级):
- **绿色(免检)**:常量最后更新在30天内,且期间无苹果新品发布、无重大行业价格事件 → 直接使用,无需校验
- **黄色(轻校验)**:常量最后更新在30-90天内,或期间有小型事件 → 执行1-2条搜索交叉验证保值率/价格趋势,无明显偏差则直接使用
- **红色(全校验)**:常量最后更新超过90天,或期间有重大事件(新品发布、官方调价、存储价格异动超过20%) → 完整执行3条宏观搜索+保值率校验

**操作**:
1. **判定常量校验级别**:根据 constants.json 的 `last_updated` 日期和近期事件,判定绿/黄/红三级
2. **分层宏观扫描**(v3.8更新,按 constants.json "宏观因素扩展模型_v3.8" 框架执行):
   - **L1_必扫层**(每次分析执行,红色级别执行3条,黄色执行1-2条,绿色跳过):
     - `苹果 涨价 调价 {当前年份} 最新` — 是否有官方涨价事件
     - `DRAM NAND 存储 价格 {当前年份} TrendForce` — 是否有存储芯片价格异动
     - `苹果 新品 发布 {当前年份} 路线图` — 是否有临近的新品发布
   - **L2_存储超级周期层**(L1检测到存储事件时触发):搜索"TrendForce 内存 见顶 预测"、"DRAM NAND 缓解 2027 2028"、"AI HBM 挤压 消费级 产能",判定周期阶段 ∈ {进行中, 见顶中, 缓解, 无事件}
   - **L3_BOM成本层**(L1/L2涉及具体品类时触发):搜索"{品类} BOM 成本 {当前年份} TechInsights"、"{具体新品} 售价 涨幅 分析师",更新 constants.json "新品发布对老款冲击._新品价格预测模型_v3.8._分品类预测涨幅表"
   - **L4_产能与缺货层**(涉及Mac Studio/Mac Pro等高延迟品类时触发):搜索"{品类} 缺货 排队 交付延迟 {当前年份}",更新 constants.json "苹果产品发布节奏._缺货等待期模型_v3.8"
3. **判断影响因素**:对搜索结果,判断是否构成影响决策的宏观因素
   - **等待新品触发判定**:查 constants.json "苹果产品发布节奏"对应品类的"下一次预计"字段,计算距分析日期的月数。≤3月 → 主动触发(步骤1生成类型B/C候选);>3月 → 被动触发(仅用户明确要求时生成);无"下一次预计" → 不触发
   - **发布时间预测校验**(v3.8新增):对涉及类型B/C候选的品类,执行 constants.json "苹果产品发布节奏._发布时间预测校验_v3.8" 校验机制。若搜索结果偏离预测≥1季度,在报告中标注"⚠️ 发布时间预测偏差≥1季度,类型B/C方案置信度降级"
4. **常量校验结论**:
   - 绿色:直接使用,记录"常量近期已校验,无需更新"
   - 黄色:记录校验结果,无偏差则使用,有偏差则标记
   - 红色:对比搜索数据,若实测保值率偏离曲线>15%标记需更新;出现新芯片标记需补充;超过12个月标记需年度更新
5. **影响传导判断与机制激活**(v3.8扩展):根据L2判定的周期阶段,激活以下机制:
   - **存储超级周期_进行中** → ①启用"缺货等待期模型.宏观产能延迟"因子=2.0;②启用"新品价格预测模型",对所有未发布新品使用预测涨幅中位数;③对"新品发布对老款冲击"均值按价格传导因子表向下修正;④在报告中标注"⚠️ 当前处于存储超级周期,新品价格预测/冲击调整/缺货延迟已启用宏观修正"
   - **存储超级周期_见顶中** → 因子=1.5,预测涨幅中位数减半,冲击修正幅度减半
   - **存储超级周期_缓解/无事件** → 全部使用默认值,不触发v3.8机制

**输出**:校验级别 + 宏观因素清单(分层) + 常量校验结论 + 调整方案 + **等待新品触发判定** + **周期阶段判定与激活的v3.8机制清单**

### 步骤3:校验市场价快照并按需更新

**核心机制**:constants.json "实时市场价快照"字段已存储已搜索的真实交易渠道价格。本步骤**优先校验快照是否可用**,仅在必要时按分级规则做最小化搜索更新,避免每次分析全量搜索。

#### 3.0 快照分级校验规则

查 constants.json "实时市场价快照.snapshot_date" 与 "_快照分级使用规则",根据分析日期与快照日期的间隔判定级别:

- **≤14天(绿色免更新)**:直接使用快照价格,仅对快照中缺失的候选机型做补充搜索
- **15-30天(黄色轻校验)**:对已有机型做1条交叉验证(京东自营当前价),偏差<5%继续使用快照;偏差≥5%或近14天有苹果官方调价/新品发布事件则对受影响机型重新搜索
- **>30天 或 近30天有苹果官方调价/新品发布(红色全更新)**:全量重新搜索,并回写更新本快照

#### 3.1 数据源优先级与搜索方法

当需要搜索/更新价格时,从agent自主操作优先、尽量减少用户介入的角度,严格按以下优先级执行(见 constants.json "实时市场价快照._数据源优先级"):

**一级_苹果官网直采**(高置信度,agent自主,无需用户介入):
- **苹果官网(apple.com.cn)**:✅ WebFetch可直接搜索静态HTML价格 → 优先使用,用于获取残值分母(当前同品类新品价)和当前在售机型的官方价

**二级_可信二手资料**(中置信度,agent自主,无需用户介入):
- 当一级无法获取二手价时,WebSearch搜索**明确写了购买日期+购买渠道+完整配置的真实成交帖**,且与宏观事实不冲突。可信来源优先级:V2EX/Reddit/什么值得买用户实付晒单 > B站视频实拍 > 论坛讨论
- **5项标准**(必须全部符合):见 constants.json "实时市场价快照._可信二手资料5项标准"

**三级_browser-use直采销售渠道**(中置信度,需用户协助登录):
- 当一二级均无法获取足够数据时,使用browser-use subagent访问闲鱼/爱回收等销售渠道
- **适用平台与搜索策略**:按 constants.json "实时市场价快照._browser_use_最佳实践" 字段执行(含前提条件、搜索策略、关键词精确化、筛选规则、步骤预算、回写快照规则)

**四级_兜底**(无法搜索):
- 标注"无法搜索(无符合标准的可信二手资料)",不得编造。**必须在报告中明确提示用户人工补充或检查**,建议用户提供具体闲鱼/爱回收/京东链接或截图(置信度可升至高)

#### 3.2 残值分母(当前同品类新品价)

**定义**:"当前同品类新品价"指该品类当前在售的最新一代**同芯片级别**产品的官方售价。
- "同芯片级别"定义:基础芯片对应当前最新基础芯片,Pro对应当前最新Pro,Max/Ultra以此类推
- 例1:Mac mini M2(基础芯片) → 残值分母用"Mac mini M6(基础芯片)官方售价"(v4.0起,6999元;原M4口径5999作历史分母保留)
- 例2:Mac mini M2 Pro(Pro芯片) → 残值分母用"Mac mini M5 Pro官方售价"(Mac mini无M6 Pro,Pro级最新为M5 Pro);若最新一代无对应芯片级别(如M4代无Pro),则用该品类当前最高配置官方售价
- 注意:不是该机型自身的原始发布价

**取值方法**:优先查 constants.json "实时市场价快照" 对应品类的"官方价"字段。若快照中已搜索(WebFetch直接搜索苹果官网),直接使用;若无,执行 WebFetch 搜索苹果官网对应品类页面。

#### 3.3 候选机型买入价搜索

**操作**:对候选机型清单,从 constants.json "实时市场价快照" 对应品类下查各机型的价格。快照中已有的字段直接使用;缺失或需更新的字段按3.1数据源优先级搜索补充。

**价格筛选规则**:
- 搜索结果中的价格必须明确标注完整配置(芯片+内存+存储),不同配置价格不可混用
- 排除无效数据:引流帖(标价极低但实际无货)、翻新机冒充二手、官翻机混入、资讯稿/导购评测文引用价(不符合5项标准)、卖家挂单价(非实付交易)
- 取有效数据的中位数作为参考价,记录样本量和价格区间
- **合理区间校验**:二手价应在同品类当前新品价的15%-85%之间(视机龄调整)。机龄12月内应在70-85%;24-36月应在45-65%;48-60月应在15-35%。超出区间需二次验证
- **置信度标注**:按 constants.json "实时市场价快照._置信度等级" 字段评定(高/中/低)
- **AC+说明**:参考价默认指不带Apple Care+的裸机价;若用户计划购买AC+,需将AC+费用按持有月数平摊计入月均成本

**配置精确化**:
- 8G与16G版本价差约20-30%,不得混用
- 256G与512G版本价差约15-25%,不得混用
- 若某配置数据不足,可基于相近配置按比例估算,标注"估算"

**置信度低的字段处理**:
- 在分析报告中**必须明确标注**置信度等级,不得作为精确决策依据
- 对缺失或低置信度的关键字段,**主动提示用户人工补充或检查**(如"⚠️Mac mini M2 16G二手闲鱼价为低置信度(论坛讨论非实付),建议用户提供具体闲鱼/爱回收链接或截图以提高置信度")
- 若用户提供具体闲鱼/爱回收/京东链接或截图,优先使用用户提供的数据(置信度可升至高)

#### 3.4 电商折扣价(仅限当前在售机型)

**搜索方法**(从快照中读取或WebSearch补充):
1. 京东自营价:查快照"京东自营价_参考"字段,或WebSearch搜索 `"{具体型号} 京东 自营 价格 {当前年}"` 寻找符合5项标准的实付晒单
2. 京东国补到手价:查快照"京东国补到手价"字段,或WebSearch搜索 `"{具体型号} 国补 到手价 {当前年}"` 寻找符合5项标准的实付晒单
3. 京东以旧换新到手价:查快照"京东以旧换新到手价"字段,或WebSearch搜索

**国补/临时补贴处理**:
- 月均成本计算使用**用户实际支付价(补贴后)**作为买入价
- 报告中单独标注补贴金额和政策时效性风险

**操作**:若本步骤执行了新的搜索,将搜索结果回写到 constants.json "实时市场价快照" 对应品类/机型字段,并更新 snapshot_date 为本次搜索日期。

**输出**:各候选机型的价格表,每个价格标注置信度等级和搜索来源URL

### 步骤4:计算持有期平均性能满足度

**静态性能满足度公式**(来自 constants.json):
```
S(0) = 芯片性能系数 × 内存权重 × 存储权重 × 100%
芯片性能系数 = 该芯片多核跑分 / 该品类当前最新旗舰芯片多核跑分
```

**持有期平均性能满足度**(考虑持有期内基准芯片更新导致的相对性能衰减):

衰减模型:苹果芯片代际多核性能提升率按系列不同(来自 constants.json "芯片代际提升假设"),持有期内该芯片相对最新旗舰的系数持续下降。

```
S(t) = S(0) / (1 + r)^(t/12)
S̄(N) = [S(0) + S(N)] / 2         持有期平均(线性近似)

r 取值(按芯片系列):
  M系列(M1/M2/.../M6): r = 0.16 (CAGR 16%/年,基于M1→M5实测跑分与发布间隔重算,v3.8更新;M6为推算值且M5→M6间隔仅5月年化失真,暂不重算,待M6实测后统一重算)
  A系列(A14/A15/.../A19): r = 0.15 (CAGR 15%/年,基于A14→A19跑分与发布间隔计算)
```

**操作**:
1. 查 constants.json "芯片性能跑分" 得该芯片多核跑分
2. 查 "性能满足度计算公式.品类基准芯片" 得基准芯片及跑分
3. 按品类选内存权重/存储权重子表
4. 代入静态公式得 S(0)
5. 对每个候选持有期 N,计算 S(N) 和 S̄(N)
6. **类型B新品性能预测**:按新品官宣状态分两支:
   - **未官宣**(v3.8原逻辑):新品为新的基准芯片,S(0)=100%。新品跑分预测 = 当前最新旗舰跑分 × (1+r)^(发布周期月/12)。S̄(N) = [100% + 100%/(1+r)^(N/12)] / 2
   - **已官宣未发售**(v4.1更新):新品跑分用 constants.json 推算条目(芯片条目"_实测说明"内含推算区间),品类基准芯片**保持最后一个实测旗舰不切换**,新芯片自身系数 = 推算跑分 ÷ 实测基准(允许 >100%),并按推算区间做敏感性标注。细则见 §9.5
   - **代际跃升模型调整**(v3.8新增):查 constants.json "芯片代际提升假设" 对应系列的"per_generation详表_v3.8",若新品信号符合"跃升代际"(架构大改/节点成熟期/核心数增加),将下一代预测的提升率上调至 r×1.5;若为节点首发代际(如2nm/3nm首发),下调至 r×0.5
7. **类型C性能**:等新品买降价老款,S(0)和S̄(N)与类型A(现在买同款)相同——性能衰减模型已通过r因子覆盖持有期内的基准更新
8. 场景修正:轻度办公 ×1.2(上限100%);专业工作流 ×0.9。修正应用于 S̄(N)

**示例**:M2 16G 256G(M系列),S(0)=48%。持24月:S(24)=48%/(1.16)^2=48%/1.3456=36%。S̄(24)=(48%+36%)/2=42%。持36月:S(36)=48%/(1.16)^3=31%。S̄(36)=(48%+31%)/2=40%

**说明**:
- r 值为基于历史跑分的CAGR(复合年增长率),非per-generation简单平均。M系列per-generation年化率波动范围9-28%,A系列6-26%,实际代际提升有较大波动
- v3.8新增"代际跃升识别":per-generation详表记录M1→M2(+31%,跃升)、M3→M4(+25%,跃升)等显著代际。节点首发代际(如A16→A17_Pro仅+6%,3nm首发)反而提升最小,因良率受限
- 近期趋势:M4→M5仅10%/年,显示放缓迹象。M6已官宣(2026-08-25):2nm首发判断命中,绝对提升+20%(官方口径),但M5→M6间隔仅5月使年化≈49%/年,趋势判断需绝对提升率与年化双口径;M7/A21(2nm成熟)可能成为下一跃升代际(年化20%+)
- 长持有期(>36月)的衰减预测置信度降低,需在报告中标注
- 此衰减仅反映"相对性能落后",不反映"绝对性能下降"——M2今天能做的事3年后一样能做,只是相对M6/M7显得落后

**输出**:各候选方案的持有期平均性能满足度 S̄(N)%,标注S(0)和S(N)

### 步骤5:计算月均成本(含持有期预期维修成本)

**公式**(来自 constants.json):
```
月均成本 = (买入价 - 预期卖出残值 + 持有期预期维修成本) / 持有月数
预期卖出残值 = 调整后保值率 × 当前同品类新品价
```

**持有期预期维修成本**:
```
预期维修成本 = 预期电池更换费用 + 预期故障维修费用
预期电池更换费用 = floor(持有月数 / 电池寿命周期) × 单次电池更换费用
预期故障维修费用 = 持有年数 × 年均故障维修费用(见constants.json)
```

**关键定义**:
- **当前同品类新品价**:定义见步骤3.2
- **机龄(发布后月数)**:定义见步骤1术语说明
- **保值率查表方法**:
  - 若卖出时机龄恰好在曲线上,直接取值
  - **线性插值**(两点之间):`保值率 = 保值率[i] + (保值率[i+1] - 保值率[i]) × (目标月数 - 月数[i]) / (月数[i+1] - 月数[i])`
  - **曲线末点(通常60月)后外推**(v3.9,替代线性外推):指数衰减,`R(t) = floor + (R(last) − floor) × 0.5^((t − last月数) / half_life_months)`,floor与半衰期查各品类曲线 `_floor`(默认3)与`_half_life_months`(默认24)。线性外推在96-120月区间会产生负残值,故弃用
  - **外推无月数上限**:超出系统支持期(macOS约72月,iOS约60月)时按指数衰减继续外推,但报告中必须标注"⚠ 超出系统支持期X月"
  - **保底**:保值率不低于3%

**操作**(对每个候选方案,即每个机型×持有期组合):
1. 买入价 = 步骤3快照/搜索的实际支付价
   - **类型A**:当前快照价
   - **类型B**(v3.8更新):若步骤2触发"新品价格预测模型",买入价 = 当前同档老款官方价 × (1 + 预测涨幅中位数);未触发时使用"同档同价假设"
   - **类型C**(v4.1更新):买入价 = 当前老款市场价 × (1 + 锚涨幅) × (1 - 调整后冲击幅度 × 冲击时变因子)。锚涨幅定义与涨价发布失效判定见步骤1类型C与 §9.4。调整后冲击幅度 = 历史均值 × (1 + 价格传导因子),查 constants.json "新品发布对老款冲击._宏观因子调整_v3.8";冲击时变因子按"新品发布后到买入的月数"查 "._冲击时变曲线_v3.8" 的"买入价下降因子"
2. 持有期末机龄 = 当前机龄 + 持有月数
   - **类型B**:持有期末机龄 ≈ 持有月数(新品买入时机龄≈0)
   - **类型C**:持有期末机龄 = 当前机龄 + 等待月数(含缺货延迟) + 持有月数
3. 查表得到原始保值率
4. **新品发布冲击调整**(仅类型A,若适用,v3.8更新):若持有期内有新品发布
   - v3.7:冲击后保值率 = 原始保值率 × (1 - 冲击幅度均值 × 50%)
   - v3.8:用"冲击时变曲线_v3.8"的"残值调整因子"替代固定50%:1月内=0.95,3月内=0.85,6月内=0.60,12月内=0.30,12月后=0.10。冲击后保值率 = 原始保值率 × (1 - 调整后冲击幅度 × 时变因子)。调整后冲击幅度同样按"._宏观因子调整_v3.8"修正
   - **注意**:此调整仅适用于类型A(现在买)。类型B(等新品买新品)和类型C(等新品买降价老款)不施加此调整——类型B买入的就是新品,无冲击;类型C的冲击已体现在买入价下降中(见步骤1类型C)
5. **宏观因素调整**(若适用):
   - 通用公式:`调整后保值率 = 原始保值率 × (1 - 预期价格回落幅度)`
   - "预期价格回落幅度" = 涨价幅度 × 预判消退比例
6. 若同时存在新品冲击和宏观因素,乘法叠加
7. 预期卖出残值 = 最终保值率 × 当前新品价
   - **类型B/C的"当前新品价"**(v3.8更新):若步骤2触发"新品价格预测模型",类型B/C残值分母用预测的新品官方价(=当前老款官方价 × (1+预测涨幅中位数));未触发时使用当前快照的同品类新品价
   - **类型A持有期内涨价发布**(v4.1新增):持有期内新品官宣涨价发布时,残值分母改用新品官宣价(锚上移),冲击项用价格传导因子对冲后的幅度——锚定与冲击两股力量乘法叠加,勿只计冲击项(见 §9.4)
8. 计算持有期预期维修成本(查 constants.json "持有期预期维修成本" 参数)
9. 代入月均成本公式
10. **等待期机会成本**(v3.8新增,可选):若用户在步骤1提供了"无设备可用的替代成本/月"(如租机费用或降级使用损失),类型B/C的月均成本 = 原月均成本 + 等待月数 × 替代成本 / 持有月数

**输出**:各候选方案月均成本,标注买入价、调整后残值、维修成本、持有月数、各项调整依据,以及触发的v3.8机制清单

### 步骤6:帕累托前沿分析与决策

**核心思想**:所有候选方案在(月均成本, 持有期平均性能)平面上构成散点,帕累托前沿(非劣解集)即为不存在"成本更低同时性能更高"的其他方案的集合。前沿上的点都是合理选择,不存在谁更优——取决于用户偏好。

**操作**:
1. **构建决策空间**:所有通过硬约束筛选的候选方案,以(月均成本, S̄(N))为坐标画散点
2. **计算帕累托前沿**:
   - 一个方案 A 被方案 B 支配,当且仅当 B的月均成本 ≤ A 且 B的S̄(N) ≥ A,且至少一个严格不等
   - 前沿 = 不被任何其他方案支配的方案集合
3. **剔除被支配点**:被支配的方案直接排除,不进入推荐(它们在前沿上无竞争力)
4. **前沿上截取推荐区间**(根据用户偏好):
   - **若用户指定了性能地板**(如"平均性能不低于50%"):在前沿上保留 S̄(N) ≥ 性能地板的段,推荐该段上成本最低的1-2个方案
   - **若用户指定了预算上限**:在前沿上保留月均成本对应的年化支出 ≤ 预算/持有年数的段
   - **若两者都未指定**:在报告中给出前沿的三档参考点:
     - 经济档:前沿最左端(成本最低,性能也最低)
     - 均衡档:前沿中段(成本和性能的中间点)
     - 性能档:前沿最右端(性能最高,成本也最高)
   - 并询问用户偏好后确定最终推荐
5. **标注不确定性**:
   - 长持有期(>36月)的保值率为外推,性能衰减为假设 → 前沿右下段置信度低,标注"预测不确定性高"
   - 短持有期(<12月)的数据点少,置信度中等
   - 12-36月区间的候选方案置信度最高

**超预算处理**:若前沿上所有方案均超预算,明确告知,在前沿下方(被支配区)找最接近预算的方案,标注"虽非前沿最优,但在预算约束下的最佳折中"。

**多品类/全品类决策**:
1. 每个品类先独立完成帕累托前沿分析,得到各品类前沿
2. 将各品类前沿上的方案放在一起,在统一的(月均成本, S̄(N))平面上再算一次跨品类帕累托前沿
3. 明确说明跨品类比较的局限性(场景差异大,量化指标仅供参考)
4. 最终推荐结合用户使用场景给出定性建议

**输出**:帕累托前沿图 + 前沿方案表 + 推荐区间 + 被支配点剔除清单

### 步骤7:输出报告(结论先行)

**报告结构**:

**第一部分:结论与推荐方案**
- 一句话结论:买什么、怎么买、持有多久
- 推荐方案表(仅含前沿上截取的推荐区间):型号、配置、**买入时机**(现在/等新品后)、买入价、持有期、月均成本、平均性能满足度、推荐理由
- 前沿备选清单:前沿上其他非劣方案,供用户按偏好选择
- **等待方案提示**:若包含类型B/C方案,标注等待月数和"预测值",提示用户评估等待期机会成本(如无设备可用期间的替代方案)

**第二部分:支撑证据**
- 帕累托前沿图(核心图表)
- 完整候选方案计算表(含被支配点及剔除原因)
- 宏观因素分析
- 常量校验结论(含校验级别)
- 维修成本估算明细

**第三部分:图表说明**
- 帕累托前沿图的阅读方法
- 前沿上各点的含义
- 不确定性标注说明

**第四部分:更新提示**
- 触发重新分析的条件
- 下次建议分析时间

```
斜率_i = (保值率[i+1] - 保值率[i]) / (月数[i+1] - 月数[i])
```

### 3.3 规律表述规范
- 基于数据统计描述,不使用预设结论式表述
- 标注统计样本来源

## 4. 数据质量保证

### 4.1 常量置信区间
- 保值率数据置信区间 ±5-10%
- 代际跨越可能导致老款额外贬值10-15%
- 偏离曲线超过15%时标注"代际差异"

### 4.2 变量搜索规则
- 二手价同一配置至少3个独立报价(或符合5项标准的可信二手资料单样本,标注中置信度)
- 所有价格通过合理区间校验
- 电商价以京东自营为准,国补使用实付价
- **优先使用 constants.json "实时市场价快照" 中的已搜索价格**,仅对缺失/过期/低置信度字段做补充搜索
- 优先级:真实交易渠道直采(苹果官网WebFetch) > 符合5项标准的可信二手资料(实付晒单) > 兜底标注"无法搜索"并提示用户人工补充

### 4.3 时效性
- 快照按分级校验规则更新(≤14天免更新/15-30天轻校验/>30天全更新,见步骤3.0)
- 变量标注搜索日期,时效30天
- 常量按三级校验规则更新(绿/黄/红)
- 年度更新每年1月进行

### 4.4 帕累托分析的不确定性
- 长持有期(>36月):保值率为外推,性能衰减率(M系列16%/A系列15%)为CAGR假设且近期有放缓迹象 → 前沿右下段置信度低
- 短持有期(<12月):数据点少,置信度中等
- 12-36月区间:置信度最高
- 报告中必须标注各候选方案的置信度等级

## 5. 禁忌清单

1. **不得预设宏观因素**:每次分析前按步骤2级别扫描,不固化"存储涨价"等因素
2. **不得预设规律结论**:规律从 constants.json 数据统计得出
3. **不得凭空给数值**:所有量化指标按公式计算
4. **不得混淆常量与变量**:常量来自 constants.json(含实时市场价快照),变量来自快照外实时搜索
5. **不得假设用户需求**:必需输入缺失时用 AskUserQuestion 询问
6. **不得使用英文缩写时间**:"2027H2"写"2027年下半年"
7. **不得把短期泡沫当长期趋势**
8. **不得先给框架后给结论**:必须结论先行
9. **必须使用中文表达,代码注释也用中文**
10. **保值率曲线年度更新**:按SOP每年1月更新,年中不修改。分析时若发现实测保值率与曲线偏差>10pp,在报告中标注"实测偏差提示"(见constants.json "贬值规律说明")
11. **等待方案价格不得回写快照**:类型B/C买入价均为预测值,不得回写至 constants.json "实时市场价快照"(快照仅记录实际搜索到的真实价格)。新品发布后应重新分析,用真实价格替换预测值

**注**:以下规则已在步骤中详述,此处仅作索引,不重复展开:
- 数据源/置信度/5项标准/挂单价非实付 → 见步骤3.1-3.3 与 constants.json "实时市场价快照._数据源优先级/_可信二手资料5项标准/_置信度等级/_browser_use_最佳实践"
- 系统支持期不作硬排除(仅标注风险) → 见步骤1.6
- 持有期是决策维度、帕累托前沿不可替代 → 见步骤1.4 与步骤6
- 每个变量必须标注数据来源、搜索时间、置信度 → 见步骤3.3 价格筛选规则

## 6. 图表规范与绘制方法

### 6.1 通用要求
- 每张图必须有:标题、横轴名、纵轴名、数据来源、阅读说明
- 移动端字号≥14px,桌面端≥12px

### 6.2 绘制技术栈
- **图表库**:ECharts(CDN引入)
- **输出格式**:单个自包含HTML文件
- **输出位置**:当前项目工作目录,文件名格式:`YYYY-MM-DD-苹果产品购买决策报告.html`(如`2026-07-21-苹果产品购买决策报告.html`)
- **移动端适配**:viewport设置+响应式容器

### 6.3 视觉与图表实现

**所有可复制代码(CSS token、组件伪代码、ECharts baseOption 与图表模板、禁止事项)的唯一权威源为 constants.json `design_tokens` 字段**。生成 HTML 报告时直接复用该字段中的代码块,不擅自修改数值;新增图表类型时仍必须合并 `baseOption` 模板。

**纪律性条款**(不依赖任何外部设计文件):
- **品牌蓝 `#007AFF` 是唯一的行动指向色**:推荐行/前沿点/关键数字/链接。推荐行高亮用 `--accent-soft`,不用 `success-soft`
- **语义色只进徽章,不大面积填充**;仅 4 种语义色(success/warning/error/default),不新增
- **前沿点/主数据线永远是品牌蓝**;被支配点用灰色半透明(`C_GRAY` + `opacity:0.5`)
- **超支持期边框用 `C_WARNING`(橙)**,不用红色——红色留给"被支配"语义
- **长持有期(>36月)的点用 `opacity:0.6`** 标注预测置信度低
- **不引外部字体 CDN,不引 Tailwind/Bootstrap 等 UI 框架**;字体栈见 constants.json `design_tokens.字体栈`
- **不用深色/渐变背景、斑马纹表格、3D 效果、多层阴影叠加、动态动画**(除 tooltip 外)
- **图表高度**:核心图(帕累托)430px / 辅助图 330px / 移动端统一 360px
- **关键数字(月均成本等)不进徽章**,直接用 `font-size:32px;font-weight:600;font-family:var(--font-display)`

### 6.4 标准图表类型

**图表1:保值率曲线图**(折线图)
- 横轴:机龄(发布后月数)
- 纵轴:保值率%

**图表2:帕累托前沿图**(散点图,核心图表)
- 横轴:月均成本(元/月)→ 越低越省
- 纵轴:持有期平均性能满足度% → 越高越好
- 每个点 = 一个(机型 × 持有期)候选方案
- **前沿点**:实心圆+品牌色,用虚线连接表示前沿
- **被支配点**:空心圆+灰色,标注"已排除"
- **硬约束排除点**:不显示(已在步骤1排除)
- 气泡大小:持有期内净支出(买入价 - 残值 + 维修成本),反映资金占用规模
- 标注:用户性能地板(若有)用水平虚线,预算上限(若有)用垂直虚线,截取前沿上的推荐区间用高亮色
- 不确定性标注:长持有期(>36月)的点用半透明或虚线边框,标注"预测置信度低"
- **等待方案标注**:类型B/C方案用不同形状(如三角形)或标签"等新品后"区分,标注"预测值"。等待月数在图例中说明

**图表3:各机型多持有期成本曲线**(折线图,辅助图表)
- 横轴:持有月数(12/18/24/36/48/60)
- 纵轴:月均成本
- 每个机型一条线
- 用于展示"持有越久月均越低但边际递减"的趋势

## 8. 示例:完整执行一次分析

**用户输入**:"想买个Mac mini,预算5000以内,不知道用几年划算"

**执行**:

2. 常量校验:黄色轻校验。**v3.8分层宏观扫描**:L1检测到2026-06-25苹果全线涨价(Mac mini涨33.3%)+存储超级周期。L2判定为"存储超级周期_进行中"。L3搜索TechInsights BOM数据更新新品预测涨幅表。L4搜索Mac Studio缺货情况。**激活v3.8机制清单**:①新品价格预测模型启用;②冲击幅度向下修正;③缺货等待期因子=2.0。发布时间预测校验:Mac mini M5预测偏差已超1季度(原预测2026-Q3,实测无任何发布迹象),标注"⚠️ 类型B/C方案置信度降级"

## 9. 特殊场景处理

### 9.1 多品类/全品类对比
当用户要求对比多个品类(如"手机和电脑哪个该先换"):
1. 每个品类独立完成候选方案生成、价格搜索/快照校验、计算、帕累托前沿分析
2. 将各品类前沿上的方案放在一起,在统一的(月均成本, S̄(N))平面上再算一次跨品类帕累托前沿
3. 明确说明跨品类比较的局限性,结合场景给出建议

### 9.2 用户指定固定持有期
当用户明确指定持有期(如"就用2年"):
1. 不展开多持有期,只生成该持有期的候选方案
2. 退化为单持有期机型对比,帕累托前沿仍适用(只是每个机型只有一个点)
3. 前沿退化为该持有期下的机型排序

### 9.3 等待新品发布场景
当步骤2检测到距新品发布 ≤ 90天,或用户明确要求"等新品":
1. 步骤1额外生成类型B(等新品买新品)和类型C(等新品买降价老款)候选方案
2. **类型B买入价预测**(v3.8更新):若步骤2触发"新品价格预测模型"(存储超级周期/全线涨价事件),买入价 = 当前同档老款官方价 × (1 + 预测涨幅中位数);否则使用"同档同价假设"。性能S(0)=100%(新品为基准),残值按正常曲线查表(不施加冲击)
3. **类型C买入价预测**(v4.1更新):买入价 = 当前市场价 × (1 + 锚涨幅) × (1 - 调整后冲击幅度 × 冲击时变因子)。锚涨幅定义见步骤1类型C;涨价发布场景的失效判定与三情景预估见 §9.4。调整后冲击幅度按"._宏观因子调整_v3.8"修正;时变因子按"._冲击时变曲线_v3.8"查表。残值按买入后机龄查表(不施加冲击,因冲击已体现在买入价中)
4. **等待月数计算**(v3.8更新):等待月数 = 预计发布月距分析月数 + 上市到货延迟(查 constants.json "_缺货等待期模型_v3.8")。若宏观扫描检测到存储超级周期_进行中,延迟×宏观产能因子(默认2.0)。报告需标注"基线等待月数"与"悲观等待月数"
5. 三种类型方案在同一帕累托前沿上比较。报告标注等待月数(含缺货延迟)、激活的v3.8机制清单,提示等待期机会成本(可选纳入等待期替代成本)
6. 新品实际发布后,应重新分析:快照触发红色全更新,用真实价格替换预测值。原v3.8预测涨幅表对应品类标记为"已发生",改用真实价

### 9.4 涨价发布场景(锚定-冲击双因子模型,v4.1)

**适用判定**:分析时点新品已官宣定价(或已发售),且官宣价高于老款现行官方价。按锚涨幅划分发布形态:

| 发布形态 | 锚涨幅 | 处理 |
|---------|--------|------|
| 涨价发布 | > +5% | 启用本节双因子模型 |
| 平价换代 | -5% ~ +5% | 走既有类型B/C逻辑(锚涨幅按0处理) |
| 降价发布 | < -5% | 走既有逻辑,锚定项使二手预估更低 |

**核心模型**:
```
锚涨幅 = (新品官宣价 − 老款现行官方价) / 老款现行官方价      ← 对比现行官方价,非首发价
冲击幅度 = 品类冲击历史均值 × (1 + 价格传导因子)             ← 传导因子按锚涨幅查表
预估二手价 = 当前二手价 × (1 + 锚涨幅) × (1 − 冲击幅度 × 时变因子)
```

**执行要点**:
1. **两股独立力量**:锚上移抬升老款替代价值(利多),代际冲击压低老款(利空)。只含冲击项的公式只能表达"跌多少",无法表达涨价发布时的"不跌反涨",会系统性高估老款降幅与类型C捡漏空间
2. **分档差异化(必查)**:同一产品线不同档次涨幅常分化,必须分档分别计算锚涨幅与传导因子,不得全线一刀切。例:2026-08 Mac mini 基础档锚涨幅 +16.7% → 传导因子 -25% → 冲击 38% 降至 28.5%;Pro 档锚涨幅仅 +4% → 因子 -5% → 冲击 36.1%——两档结论方向相反(基础款二手利多,Pro 档利空)
3. **三情景输出**(发布窗口期1-3月预估,输出区间而非点值):
   - 情景A 全额传导:冲击 × 时变因子全额落地,作为保守下界
   - 情景B 实证口径:取最近一次同类涨价发布事件的实测冲击,查 constants.json "新品发布对老款冲击._涨价发布实证参考_v4.1";无同品类事件时用形态最接近的跨品类事件并标注外推
   - 情景C 零冲击:锚定全额传导、冲击≈0,作为乐观上界(缺货+惜售环境)
   - 三情景概率加权得出中枢
4. **概率赋值四问**(写入报告依据):①老款是否已停产/稀缺化?②新品缺货概率高吗(首发制程、存储周期、限购政策)?③需求端有无结构性增量(如本地AI)?④涨价前二手是否已透支一轮涨幅?——供货是决定性变量,预购/发售日的到货周期数据出现后,优先用其修正情景概率

**对购买决策的传导**(本节最终用途):
1. **类型B(等新品买新品)**:官宣价已知 → 买入价直接用官宣价,不再用预测涨幅外推;残值分母切换为官宣价
2. **类型C(等降价捡漏)**:涨价发布时大概率失效——用双因子模型三情景加权预估买入价,加权买入价 ≥ 当前市场价时不生成类型C候选,或生成但标注"⚠ 涨价发布,预估买入价不低于当前价,等待无收益"。实证:2025-09 iPhone 17 涨价发布后老款一周仅跌 2-4%、两月后归零,"等新机发布买旧款捡漏"窗口关闭
3. **类型A残值**:持有期跨越发售日时,残值分母用新品官宣价(锚上移),冲击项用对冲后幅度,两股力量乘法叠加(见步骤5操作7)
4. **卖出时机标注**:用户持有老款且计划短期出手时,在报告"更新提示"标注"官宣至发售后首月为高位窗口"

**边界与禁忌**:
- 本模型预估的是**发布窗口期(1-3月)价格**,不修改保值率曲线;残值计算仍走步骤5公式,锚定效应通过残值分母切换体现
- 预测值不回写快照(禁忌11);新品发售后用实测复核:发售后2周实测二手价偏离加权中枢超过 ±10% 时触发重分析
- 品类冲击均值与实证口径差距大时(如 Mac_mini 均值38%无实测来源),情景A与情景B天然分歧,必须输出区间而非点值

### 9.5 官宣未发售窗口的性能数据处理(v4.1)

**适用判定**:分析时点新品芯片已官宣但未发售,其跑分为推算值(constants.json 芯片条目带"_实测说明"且标注"推算值/待实测回填")。本节与 §9.4 同窗口互补:§9.4 管该窗口的**价格**不稳定(三情景区间),本节管**性能**数据不确定(推算区间敏感性)。

**核心规则**:
1. **基准芯片保留实测口径**:品类基准芯片(性能系数分母)保持最后一个**实测**旗舰,不用推算芯片做基准。理由:分母若用推算值,其估算误差会传导到该品类全部老款系数且不确定性被隐藏;保留实测基准则误差只落在新芯片自身一项、且显式可见
   - 例外:推算置信度高的条目可提前切换(如按历史倍率推算的 Ultra 融合芯片,Mac_Pro 基准已随 M5 Ultra 官宣切至推算口径),以 constants.json "品类基准芯片" 当前口径为准
2. **新芯片自身系数允许 >100%**:系数 = 推算跑分 ÷ 实测基准跑分,可超过100%(表示超出当前实测旗舰),S(0)/S̄(N) 照常代入衰减公式。例:M6 推算多核 21000 ÷ M5 实测 17100 ≈ 123%
3. **区间敏感性(必做)**:用推算区间两端分别计算新芯片 S(0),报告标注如"S(0)=123%(推算区间120-127%,待实测回填)"。若区间两端使帕累托前沿的**推荐方案发生改变**,必须输出两种口径的前沿对比,不得只给点值
4. **报告标注**:凡性能计算用到推算跑分的候选,在推荐方案表与性能图表中标注"⚠️ 跑分为推算值,待实测回填"
5. **实测回填触发**(发售日后,新芯片 Geekbench 实测入库时):①回填跑分条目并删除"推算值"标注;②品类基准芯片切换为新芯片,该品类全体系数重算;③M系列 r 值统一重算(见步骤4说明,M6 推算期暂缓);④若某老款候选 S(0) 因基准切换变化超过 ±5 个百分点、或推荐方案排序改变,在报告"更新提示"注明"性能基准已切换,建议复核"
   - 基准切换会使该品类全系 S(0) 绝对值下移(相对最新旗舰的口径变化),但候选间**相对排序不变**(比值不变),帕累托结论通常稳定——报告复核提示中说明这一点,避免误读为"老款突然变差"

**变体折算**:芯片条目内含变体说明(如"_15核变体说明")时,分析对应基础款须按说明折算跑分——Mac mini M5 Pro 基础款按多核 25892 而非条目值 28500 计算,直接用条目值会高估系数约 10%
