## Context

`apple-value-engine` 是 skill 端与小程序端共用的纯函数计算引擎（帕累托前沿）。SOP 自 v3.8 演进到 v4.1/v4.2 的过程中，规格与 SOP 文字已更新，但三处引擎实现未跟上；同时 v4.0 起常量库出现新数据形态——**快照可含「已官宣未发售」的新品条目**（如 2026-08-25 官宣、9-22 发售的 Mac mini M6）——候选生成器未识别这种形态。2026-08-28 Mac mini 分析被迫用人工后处理脚本（`scripts/mac-mini-postprocess-20260828.mjs`）修正引擎输出才能得到正确前沿。

三处问题定性（均已核实源码与规格）：

| # | 现象 | 定性 | 源码位置 |
|---|------|------|---------|
| 1 | M6（锚定品）被生成为类型C候选，自身价被乘锚涨幅再打折（伪影价 5211 元） | 语义错误：`extractWaitCandidates` 把快照内全部在售机型当「老款」 | `pareto.ts` extractWaitCandidates |
| 2 | M6 的 S(0) 被截断在 100%（推算口径应为 104.4%） | 规格违背：`Math.min(1, …)` 与 performance-models.md §1.2 规则2「新芯片自身系数允许 >100%」冲突 | `performance.ts` computePerformance L63 |
| 3 | 类型A老款残值未施加新品发布冲击调整 | 规格违背：spec「月均成本计算」与 SKILL.md 步骤5.4-4 均有 MUST，`cost.ts` 模块头注释「留给 skill 层」是 v3.8 时代过时决策 | `cost.ts` / `pareto.ts` buildPlanPoint 类型A分支 |

附带隐患：`getCurrentNewPrice`（残值分母取值）依赖快照键插入顺序——当前 M6 条目恰好排在首位才返回 6999（快照 `_说明` 明文规定 v4.0 起残值分母为 M6 官方价 6999），数据重排后会静默漂移回 5999。

关键数据事实（决定设计选型）：

- `发布节奏.Mac_mini.下一次预计` 已是自由文本「已发生:2026-08-25官宣M6+M5 Pro,9-22发售。下一次:约2028年中…」——**从文本解析芯片名脆弱**，但 `parseReleaseMonth` 能稳定解析出「2026-08」。
- `productReleaseDates` 含 `Mac_mini_M6 => 2026-08`、`Mac_mini_M5_Pro => 2026-08`（官宣时数据维护同步写入），老款 M4=2024-10。
- `chipBenchmarks.Mac芯片.M6.多核 = 21000`（推算值，实测说明标注待 2026-09-22 回填）；品类基准芯片仍为 M5 实测 17100 → 系数 122.8%，× 16G 内存权重 1.0 × 256G 存储权重 0.85 = S(0) 104.4%。
- `预测涨幅表.Mac_mini`：「已官宣」+ 中位数 16.7%；`新品发布对老款冲击.Mac_mini.均值 = 35%`；传导因子表 15-30% 档 = −25% → 调整后冲击 = 0.35 × 0.75 = 26.25%。

## Goals / Non-Goals

**Goals:**

- 三处口径修正后，含「已官宣未发售新品」快照的场景引擎直出正确结果，消除人工后处理环节。
- 附带加固残值分母取值，消除对快照键顺序的隐性依赖。
- 修正后用 2026-08-28 真实常量重跑，类型A各行数值与人工后处理基准（`scripts/debug/mac-mini-corrected-20260828.json`）一致，作为验收。
- 对外 API 兼容：`DecisionParams`/`PlanPoint` 字段形状不变，`computeMonthlyCost` 等函数新增参数均为可选。

**Non-Goals:**

- 类型C**三情景加权与失效判定**不入引擎（维持 spec 既有分工：引擎只出情景A「全额传导」口径，失效判定走 SOP 文字路径，见 release.ts 既有注释）。
- 推算跑分**区间敏感性**（20500-21700 两端重算）不入引擎——SOP/report 层职责。
- 类型B虚拟候选与快照锚定品条目的**去重/统一口径**不做：类型B S(0)=1.0（基准自指）与快照 M6 类型A S(0)=104.4%（推算相对实测基准）是两种合法口径，SOP 保留类型B作「国补不可得」敏感性参考，被支配无害。
- 不修 `getCurrentNewPrice` 之外的快照遍历逻辑，不改 constants.json 数据结构。

## Decisions

### D1 锚定品识别：按发布月比较，不解析节奏文本

**决策**：某候选是「锚定品（即将发布的新品本身）」当且仅当其 `productReleaseDates` 发布月 ≥ `releasePlan.nextReleaseMonth`。类型C生成时跳过锚定品。

**理由与备选**：
- 备选A（解析「下一次预计」文本中的芯片名，如「官宣M6+M5 Pro」）：文本是自由格式（含「已发生:」「下一次:」等多段），正则脆弱，弃用。
- 备选B（候选发布月 ≥ 分析月）：会误伤「上个月刚发售、等下一次发布后捡漏」的正当老款——例如 8 月刚发布的机型等 11 月新品发布后买折扣价是合法类型C，弃用。
- **选定方案**（发布月 ≥ nextReleaseMonth）：M6（2026-08 ≥ 2026-08）与 M5 Pro（2026-08 ≥ 2026-08）被排除，M4（2024-10 < 2026-08）保留——语义精确（「属于本次发布批次」），且 `productReleaseDates` 与节奏字段由数据维护者在同一次官宣回填中同步写入，一致性有保障。即使漂移，后果是伪影候选**可见地**重现（出现在输出里），不是静默错误。
- 兜底：候选 releaseDateKey 无法解析出发布月时**保守保留**（维持旧行为，不因识别失败丢候选）。

**复用**：同一判定函数供 D3 使用——锚定品自身作为类型A候选买入时，其残值也不施加「自己这场发布会」的冲击。

### D2 去除 S(0) 的 100% 截断

**决策**：`computePerformance` 中删除 `Math.min(1, chipCoeff × memWeight × storageWeight)` 的 `Math.min`，直接用乘积。

**理由**：老款芯片跑分天然 ≤ 品类旗舰（分母即旗舰），系数 ≤ 1，删除截断不改变任何老款结果；唯一行为变化是推算跑分超过实测基准的新芯片（正是 bug 本体）。不设上限钳制——推算/实测比自然有界（历史最大约 1.3），人为上限会再次制造同类 bug。类型B路径（`computePerformanceForNewProduct`，S(0)=1.0 固定）不动。

### D3 类型A残值冲击：在 buildPlanPoint 实现，调整后冲击抽共享 helper

**决策**：
1. `release.ts` 新增 `computeAdjustedImpact(constants, releasePlan, macroContext)`：调整后冲击 = 品类冲击均值 × (1 + 价格传导因子(锚涨幅或宏观预测涨幅))。逻辑从 `predictDiscountedOldPrice` 中抽出复用（该函数现内部已有同样计算）。
2. `buildPlanPoint` 类型A分支增加冲击调整，触发条件全部满足才施加：
   - 存在 releasePlan 且 `analysisMonth < nextReleaseMonth ≤ analysisMonth + holdingMonths`（持有期内有新品发布）；
   - 候选**非锚定品**（复用 D1 判定；买新品的人不受「新品发布」冲击）；
   - 品类冲击均值 > 0。
3. 调整公式（对齐 SKILL.md 步骤5.4-4）：`冲击后保值率 = 原始保值率 × (1 − 调整后冲击 × 残值调整时变因子)`；残值调整时变因子按**卖出点距新品发布的月数** = `(analysisMonth + holdingMonths) − nextReleaseMonth` 查 `_冲击时变曲线_v3.8`（复用既有 `lookupImpactTimeVaryingFactor`）。
4. 只计**下一次已知发布**一次：更远期的换代贬值已由保值率曲线（经验曲线，含平均换代贬值）覆盖，冲击调整只修正「临近发布的瞬时额外贬值」。这是方法论边界，不是遗漏。

**实现位置**：放在 `buildPlanPoint`（pareto.ts）而非 `computeMonthlyCost`（cost.ts）——cost.ts 保持「基础月均成本」纯度，冲击调整需要 releasePlan/macroContext 上下文，由持有它们的 pareto 层施加。`computeMonthlyCost` 不改签名。

**验证锚点**（M4 二手 4200、M6 官宣场景，引擎整月口径）：持有12月 → 距发布12月 → 因子0.30 → 0.35×0.75×0.30 = 7.875% 冲击；持有≥18月 → 「12月后」→ 因子0.10 → 2.625%。与人工后处理基准（日历精确11.2月→0.30）一致。

### D4 残值分母显式选「最新发布月 · 基础款」

**决策**：`getCurrentNewPrice` 改为：在快照「新品」且含官方价的条目中，选 `productReleaseDates` 发布月最晚者；**同月并列时优先基础款**（芯片名不含 Pro/Max/Ultra 后缀）。无任何可解析条目时兜底维持旧行为（首个含官方价条目）。

**理由**：当前实现按 `Object.entries` 插入序取第一个，M6 恰好排首位才返回 6999；重排即静默漂移。显式规则（最新发布月 + 基础款优先）与快照 `_说明` 的 v4.0 口径（「残值分母用 Mac mini M6 基础款官方售价6999元」）吻合：M6（2026-08，基础）与 M5 Pro（2026-08，Pro）同月，基础款优先 → 6999。不用正则解析 `_说明` 人读文本。

### D5 类型B生成保留

**决策**：快照已含锚定品条目时，类型B虚拟候选（「下一代新品」）仍照常生成，不去重。

**理由**：SOP 用它做「国补不可得」敏感性（M6@官网6999 vs M6@国补5949.2）；在 (月均成本, 性能) 平面上被快照锚定品类型A支配，保留无害。S(0)=1.0 与 104.4% 的口径差异在报告中由 SOP 层标注（「⚠️ 跑分为推算值」）。

## Risks / Trade-offs

- **[节奏字段与 productReleaseDates 漂移 → 伪影候选重现]** → 后果可见（异常低价候选出现在输出），非静默；tasks 中用镜像 2026-08 真实常量形态的测试夹具锁行为。数据维护约定（官宣时同步回填两处）写入 tasks 的文档项。
- **[S(0)>100% 冲击下游渲染]** → 小程序/报告端若按 0-100% 硬编码渲染会出现 104%。缓解：tasks 含快照/展示层检查项；SOP 报告规范本就要求推算口径标注。
- **[历史数值不可复现]** → 含官宣新品的场景数值变化正是修复目标；无官宣新品的常规场景（老款系数≤1、无冲击路径）数值不变。「skill 与小程序结果一致性」不受影响（两端同一引擎包）。验收以 2026-08-28 人工后处理基准为准（类型A行）。
- **[类型C引擎口径仍是情景A下界]** → 与人工后处理基准在类型C行上**预期不一致**（人工侧已按三情景加权判失效整体剔除）——这是 spec 既有分工，非本次回归；在验收比对时排除类型C行。
- **[整月 vs 日历月舍入]** → 引擎按整月算「距发布月数」（M4×12月 → 12 → 0.30），人工基准用日历精确月（11.2 → 0.30），本场景恰好同档位；极端边界（恰在档位分界，如 12.0 vs 11.9）可能有 0.30/0.10 之差，验收容差按「保值率因子档位一致」判。

## Migration Plan

纯代码变更、无数据迁移：实现 → 测试 → 构建（dist 重新编译）→ 用真实常量跑验收脚本比对 → 提交。回滚 = revert 单个 commit。小程序快照机制不受影响（快照同步的是 constants.json，非引擎产物）。
